## 1. 结论

三项能力都在真机跑通，但**预热池与预打包运行环境组合使用时存在一个必须先修的缺陷**。

| # | 能力 | 结论 |
|---|---|---|
| 1 | 数据面 OD/Spot 双节点组（控制面组不受影响） | ✅ **通过** |
| 2 | `r8i.8xlarge` amd64 数据面完整生命周期 | ✅ **通过**（首次） |
| 3 | 预打包运行环境 `claude-code` / `openclaw` | ✅ **通过**（含 suspend/resume 后仍可用） |
| 4 | 单 AZ 亲和节点预热池：替换加速 | ✅ **通过**，5m03s → **44s** |
| 5 | 预热池节点上的命名 rootfs 模板 | ❌ **失败**：模板全部缺失，`image=claude-code` 静默退化成 `min` |

## 6. 节点预热池（✅ 加速显著，❌ 模板缺失）

### 6.1 配置落地

```json
// aws autoscaling describe-warm-pool（OD 组）
{"MaxGroupPreparedCapacity": 2, "MinSize": 1, "PoolState": "Stopped",
 "InstanceReusePolicy": {"ReuseOnScaleIn": true}}
// 实例：i-0c40273528ceb33da  Warmed:Stopped  Healthy
```

- `MaxGroupPreparedCapacity = 2` = `desired(1) + warm(1)`，与 terraform 传参一致。
- Spot 组 `describe-warm-pool` 返回 `null` → `sandbox_warm_pool_target=od` 生效。
- ASG `HealthCheckGracePeriod = 900`、`AvailabilityZones = [us-east-1a]`。
- 预热实例 `CpuOptions.NestedVirtualization = enabled` → **启动即可跑 Firecracker**。
- 预热实例自带 `/dev/sdf` 400 GB 卷、`DeleteOnTermination=false`（成本警告成立）。

### 6.2 替换加速：5m03s → 44s

对照组（冷启动，Spot 节点 `i-0ea534d2c3c9da289`）：

```text
EC2 LaunchTime      2026-08-13T12:07:12Z
Node 注册            2026-08-13T12:10:01Z
Node Ready          2026-08-13T12:12:15Z   → 冷启动 5m03s
```

实验组（`aws autoscaling terminate-instance-in-auto-scaling-group --no-should-decrement-desired-capacity`）：

| 时刻（UTC） | 事件 |
|---|---|
| 12:39:54 | 发起 terminate |
| 12:39:57 | ASG 开始终止 `i-0d1a16eecece42e7f` |
| 12:40:09 → 12:40:16 | `Launching a new EC2 instance from warm pool: i-0c40273528ceb33da`（**7 s**） |
| 12:40:11 | ASG 同时开始补预热实例 `i-063faf3659de03f17` |
| 12:40:28 | 新 Node 对象注册（`ip-10-0-101-120`） |
| 12:40:38 | **Node Ready** |

**terminate → 新节点 Ready = 44 秒**，比冷启动 5m03s 快约 **6.9 倍**，
显著优于文档里写的「压到 1-2 分钟」。node-agent DaemonSet 在 107 s 内自动覆盖新节点。
预热池随后自动补齐 1 台 `Warmed:Stopped`（`MinSize=1` 生效）。

### 6.3 ❌ 缺陷：预热池节点上的命名 rootfs 模板全部缺失

从预热池起来的新节点 `ip-10-0-101-120`（`i-0c40273528ceb33da`）：

```text
/opt/sbx/rootfs.ext4   2 GiB   ← 只有默认 min
/opt/sbx/vmlinux       36 MiB
（rootfs-web.ext4 / rootfs-claude-code.ext4 / rootfs-openclaw.ext4 全部不存在）
```

直接调该节点的 node-agent 造一个 `rootfs_template=claude-code` 的 microVM：

```text
POST /vm/create {"id":"warmtest1","rootfs_template":"claude-code"}
  → {"state": "running", "ip": "172.18.30.2"}        ← 不报错
POST /vm/exec   cat /etc/sbx-image; which claude
  → {"rc": 0, "stdout": "NO-sbx-image-file\nNO-CLAUDE-BINARY\n"}
```

即**沙盒起得来，但里面没有 Claude Code**。`_rootfs_template_path()`
（`node-agent/main.py:94-104`）在模板查不到时按设计静默回退默认 min，
API 层不会报错、`/admin/images` 也照样列出 `claude-code` → 用户拿到一个空壳。

**根因**（`last reboot` + ASG activity 实测）：

```text
预热实例第一次开机   12:10 – 12:11（约 1 分钟）→ 被 ASG 停机
ASG "Launching into warm pool" Successful  12:12:12
```

对照正常节点的 pre-bootstrap 时间线（`ls --time-style=full-iso /opt/sbx/`）：

```text
12:07:30  vmlinux
12:08:42  rootfs.ext4（min）
12:09:02  rootfs-web.ext4          (+20 s)
12:09:29  rootfs-claude-code.ext4  (+27 s)
12:09:56  rootfs-openclaw.ext4     (+27 s)   → 造 4 个模板共约 2m26s
```

ASG 把「EC2 running + 健康检查通过」当作预热完成就停机，**不等 cloud-init 跑完**；
预热实例只活了约 1 分钟，刚造完 min 就被停掉，三个命名模板（229+194+53 MiB 下载 +
`dd`/`mkfs.ext4`/解包，约 74 s）全部没来得及执行。停机后 `cloud-init-output.log`
里 `grep -c "rootfs template"` = **0**。

**副作用**：预热实例第一次开机也没来得及跑完 nodeadm bootstrap，
所以它**不会**先 join 集群 —— `kubectl get nodes` 全程只有 4 个 Node 对象，
没有出现 NotReady 的预热 Node。这与既有文档里的警告相反，已同步更正（§8）。

**修复方向**（本次未实施，属下一轮）：

1. **把模板烤进自定义 AMI**（文档里本来就写的下一步）—— 一劳永逸，同时也解决冷启动 2m26s。
2. 给 node-agent 加**启动时模板自愈**：对比 `SANDBOX_IMAGES` 与 `/opt/sbx/rootfs-*.ext4`，
   缺失就异步补拉（幂等），补齐前对该 image 的 create 返回明确错误而不是静默回退。
3. 或者用 ASG 生命周期钩子（`autoscaling:EC2_INSTANCE_LAUNCHING` + heartbeat）
   让 warm pool 等 pre-bootstrap 完成 —— 能治本但最复杂，且延长预热实例的计费开机时间。

短期规避：`sandbox_warm_pool_size > 0` 时不要依赖 `rootfs_images`
（只用默认 `min`），或反之。

### 6.4 幸存状态卷不会自动复用（与文档一致）

| 卷 | 大小 | 状态 | 挂载 |
|---|---|---|---|
| `vol-0d4839478aced8fe1` | 400 GB | **available（孤儿）** | 无 —— 被终止的旧 OD 节点留下 |
| `vol-0dbde2b132b213e35` | 400 GB | in-use | `i-0c40273528ceb33da`（新 OD 节点，用的是它自己作为预热实例时的卷） |
| `vol-040e082bb66559a86` | 400 GB | in-use | Spot 节点 |
| `vol-0937a493835c9b50f` | 400 GB | in-use | 新补的预热实例 |

坐实：节点替换后旧节点的状态卷**残留为 `available` 孤儿卷**，新节点用自己的空卷，
**没有任何自动 detach/attach**。跨机恢复仍需人工/编排介入。
卷上只有 `Name` / `eks:cluster-name` / `eks:nodegroup-name` 三个 tag，
**没有统一项目 tag** → 共享账号里按 tag 审核孤儿卷这件事目前做不到（`default_tags` 仍是待办）。

另外注意：预热池会把「每台节点一块 400 GB 持久卷」变成「节点数 + 预热数」块，
本次 4 台实例 = 4 块 400 GB gp3 常驻计费，其中 1 块挂在**停机**实例上。

## 7. Spot 回收链路（✅ DRY-RUN 决策正确）

stage2 新接线的三个变量确实注入到了 node-agent DaemonSet：

```text
RECLAIM_WATCH_ENABLED=1   RECLAIM_AUTO_EVACUATE=0   RECLAIM_POLL_S=5
```

在 Spot 节点上注入一个中断信号（`POST /reclaim/simulate`，因为真实 IMDS 信号无法人为触发）：

```json
{"node":"ip-10-0-101-39.ec2.internal",
 "signal":{"type":"spot-termination","action":"terminate","injected":true},
 "count":1,"sandboxes":["841ca18d"],"est_evac_s":21.3,"mode":"DRY-RUN"}
```

node-agent 日志：

```text
[reclaim] SIGNAL=spot-termination → evacuate 1 sandboxes on ip-10-0-101-39.ec2.internal (mode=DRY-RUN, est~21.3s): ['841ca18d']
[reclaim] DRY-RUN: 不实际疏散。设 RECLAIM_AUTO_EVACUATE=1 开启真疏散。
```

`GET /reclaim/status` 随后 `detected=true`、`plan` 完整、`evacuated=false`。
检测 → 选沙盒 → 估时 → 决策这条链路正确，且**默认确实不动手**。

⚠️ 本次**没有**验证 `RECLAIM_AUTO_EVACUATE=1` 的真疏散，也没有验证真实 Spot 回收
（AWS 不提供人为触发 2 分钟通知的手段）。`_evacuate_local` 仍是串行，
客户建议的并发 6-8 未实现；疏散完成后的跨机拉起仍无自动化（见 §6.4）。

## 8. ❌ 控制面不会把沙盒投向 Spot 池

连续创建 5 个沙盒（3 × `min` + `claude-code` + `openclaw`），**全部落在 OD 节点**
`10.0.101.177`，Spot 节点 `10.0.101.39` 一个都没拿到。

原因在 `sandbox-api/drivers/firecracker.py:235` `_pick_node()`：按注册表里的
`free_mem_mib` **降序**取第一个可达节点，完全不看 `capacity-type`。两台同规格
`r8i.8xlarge`（256 GiB）上跑几个 4 GiB 沙盒，排序几乎不变 → 始终同一台。

也就是说：**双池已经能建出来，但客户决策里「无配置通道、无主动任务下发的用户实例进
Spot 池」这条分流策略还没有实现**。本次为验证 Spot 节点可用性，临时把
`FC_NODES` 指到 Spot 节点才把沙盒创到了那一侧
（顺带发现：`FC_NODES` 只是 DynamoDB 节点注册表不可用时的回退，注册表可用时
改 `FC_NODES` 不影响调度落点 —— `docs/deploy.md` 里「改完可热更新」的说法需要限定条件）。

下一轮要做的是：create 支持 `capacity_type` / 租户策略提示，`_pick_node`
按 `capacity-type` label 分流，并在 Spot 侧默认拒绝有活跃任务信号的实例。

## 9. 附：amd64 模板构建机做法

Mac 上无法交叉构建（§5.1），本次用一台一次性 EC2：

```bash

# 只打 build-rootfs-image.sh 会因缺 scripts/vsock-exec-agent.py 失败）
tar czf /tmp/builder-kit.tar.gz scripts .sbxkeys/sbx_exec.pub
```

## 11. 清理

```bash
# 沙盒 → stage2 → phase3 → stage1，最后核对 400G 孤儿卷与构建机 IAM
terraform destroy   # stage2-control-plane（同 apply 参数）
terraform destroy   # phase3（同 apply 参数）
terraform destroy   # stage1-dynamodb
aws ec2 describe-volumes --filters Name=size,Values=400 --query 'Volumes[?State==`available`]'
```

⚠️ 数据面状态卷 `delete_on_termination=false`，**destroy 不会删它们**；
本次共 4 块 400 GB gp3 需要手工确认后删除。共享账号里同尺寸卷可能属于他人，
删除前必须逐块核对 `eks:cluster-name=claude-sbx` tag。

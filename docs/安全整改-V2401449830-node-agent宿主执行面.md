# 安全整改:node-agent 宿主执行面未鉴权(V2401449830 / AD-1)

> 审计版本:`e6d992fcb62d80527aa42dc3b9c24359b59fe228`
> 整改分支:`fix/node-agent-host-plane-auth`

## 1. 结论

**确认是安全问题**(不是预期行为),严重度为严重。node-agent 以 root 运行在每台沙盒节点上，监听 `0.0.0.0:8002`,却没有任何鉴权。
它唯一的防护是 `ALLOWED_CALLER_CIDR`,而这个值默认为空(即放行所有来源),仓库里也没有任何地方设置它。
guest 的默认路由指向宿主 tap 网关，宿主 INPUT 链没有任何过滤规则。因此任一租户代码都可以:

- 枚举本节点所有沙盒，以 root 身份在任意同节点租户的 guest 内执行命令,
  并通过反代访问其任意端口;
- 对任意沙盒执行销毁、挂起、恢复、快照;
- 借 `/vm/resume` 的 `snapshot_local_path` / `rootfs_path` / `s3_prefix`,
  以宿主 root 身份往任意宿主路径写入文件(`os.makedirs` + `aws s3 sync` + `cp`)。
  宿主进程模式下可以写 `/etc/ld.so.preload`,从而拿到宿主 root 代码执行;
  在两种部署模式下都可以篡改 `/opt/sbx` 模板和 `/var/lib/sbx` 下其他租户的快照，实现持久化的跨租户入侵。

整改过程中额外发现两条相关路径，已一并修复:

- **E1** guest 流量经 NAT 后能访问 IMDS(169.254.169.254),拿到节点实例角色凭据。
  phase3 中这个角色挂的是 `AmazonS3ReadOnlyAccess`,可读账号内所有桶。
- **E2** 同节点不同 guest 的 tap 之间，以及 guest 到其他节点 node-agent 之间，都没有 FORWARD 隔离。

DaemonSet 额外收敛了两处:

- 关闭 `hostPID`。node-agent 只管理自己拉起的 Firecracker 子进程，关闭后 `/proc/1/root` 不再指向宿主根文件系统。
- `/opt/sbx` 改为只读挂载，防止模板和 kernel 被投毒。

## 3. 客户影响 / 是否破坏性变更

**这是破坏性变更，升级时控制面和 node-agent 必须一起发布。**

- 新版 node-agent 拒绝一切未签名请求。旧控制面调用新 node-agent 会收到 401;新控制面在没有密钥时不会发出请求。
  用 `terraform apply` 会同时更新 Secret、Deployment 和 DaemonSet。推荐顺序:先推镜像，然后 `terraform apply`,再滚动两者。
  滚动期间新旧版本混跑会导致短暂的创建/exec 失败。
- 直接 `curl http://<node>:8002/vm/...` 的运维脚本或手工调试方式不再可用，需要带签名(参考 `sandbox-api/node_agent_auth.py`)。
  `/health`、`/livez`、`/readyz`、`/metrics` 不需要签名。
- guest 无法再访问 IMDS。JuiceFS 模式(`enable_juicefs`,默认关闭)下,guest 如果依赖节点实例角色凭据挂载 S3,需要改为下发按沙盒收窄的临时凭据(后续项 F2)。
  原来那条路径本身就是跨租户凭据泄露。
- guest 之间不再能直接互通(同节点 tap 之间)。对外暴露的端口仍然走控制面网关 `/s/{id}/{port}/`,不受影响。
- 依赖 `/reclaim/simulate` 的验证流程需要显式设置 `NODE_AGENT_ENABLE_TEST_HOOKS=1`。
- **首次上线和密钥轮换都会重启 DaemonSet**,microVM 是 node-agent Pod 的子进程，会随 Pod 一起被终止(这在任何 node-agent 升级时本来就会发生)。上线前须先 suspend 或疏散节点上的沙盒。
  轮换时，控制面会先换到新密钥，在 DaemonSet 滚动完成之前，node-agent 调用会返回 401,所以请安排在维护窗口内进行。
- 沙盒节点组设置 IMDS hop limit 1 之后，节点上依赖 IMDS 的非 hostNetwork Pod(例如第三方日志/监控 agent)将无法获取凭据，需改用 IRSA。
- 宿主隔离不覆盖 NodePort:guest 访问宿主 IP 的 NodePort 时，流量会被 kube-proxy DNAT 到 Pod,走 FORWARD 链，与 guest 访问其他 VPC 服务等价。目前 node-agent 没有对应的 Service,不受影响。
- stage2 新增 `hashicorp/random` provider,lock 文件已更新;需要重新执行 `terraform init`。
- 密钥轮换:`terraform apply -replace=random_password.node_agent_auth`,Pod 注解会变化，从而自动触发两边滚动。

## 5. 残余风险与后续项(建议排期)

| ID | 事项 | 说明 |
|---|---|---|
| F1 | 按节点派生密钥、绑定目标节点 | 当前所有节点共用一把 HMAC 密钥，canonical 中也不含目标节点，因此在 300s 窗口内，窃听到的签名请求可以重放到其他节点(前提是能在 VPC 内窃听)。拿到某节点 root 的攻击者也可以签名调用其他节点。可改为 `HMAC(master, node_ip)` 派生，并把 Host 纳入签名;同时支持新旧两把密钥并存，实现不中断轮换 |
| F2 | JuiceFS 凭据 | 为每个沙盒下发收窄到其 workspace 前缀的 STS 临时凭据，替代 IMDS |
| F3 | 安全组 | 沙盒节点 SG 的 8002 入站只放行 system 节点 / 控制面所在 SG(需要拆分 phase3 共用的 node SG) |
| F4 | 传输加密 | 控制面 → node-agent 目前在 VPC 内使用明文 HTTP。签名可防篡改、防重放，但不防窃听 body。可升级为 mTLS |
| F5 | jailer | `USE_BARE_FC=1` 默认未启用 jailer chroot/seccomp,应在生产环境切换(见 `docs/fc-生产就绪-gap分析.md`) |
| F6 | tap_idx 回收 | `alloc_tap_idx` 是全局单调计数，没有回收。超过 255 后 `172.18.{idx}` 会成为非法地址，guest 网络不可用(这是原有问题，只有 vsock exec 可用)。node-agent 有意不在这里拒绝，以免累计约 255 次创建后所有 create 都失败。需要实现按节点分配和回收 |
| F7 | 节点上的 Pod 直连 guest | 同节点 Pod 可以经 `eni* → fctapN` 直接访问 guest,绕过网关和 `EXPOSE_TOKEN`(原有问题)。可对 `-o fctap+` 只放行宿主自身发起的流量 |

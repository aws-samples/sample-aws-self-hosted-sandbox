# 控制面与数据面分离 i7i 真机测试报告

> 实测日期：2026-08-11（Asia/Shanghai）
> 区域：`us-east-1`
> 范围：EKS 节点池分离、异构镜像、Firecracker 生命周期、快照恢复、
> LiteLLM/Bedrock、控制面故障转移与资源清理

## 1. 结论

**应该拆分控制面与数据面，本次已完成实现并通过真实 AWS E2E。**

控制面、LiteLLM、CoreDNS 等稳定组件运行在独立的 On-Demand Graviton system
节点组；Firecracker node-agent 和 microVM 只运行在专用 i7i 数据节点组。这样可以：

- 保证数据节点扩缩、故障或未来切换 Spot 时不会同时带走控制面；
- 避免高密度 microVM 的 CPU、内存和 I/O 压力挤占 API、调谐、快照编排和 DNS；
- 分别选择适合的架构和采购模型：控制面用小型 arm64 On-Demand，数据面用
  amd64 i7i，未来可按池选择 On-Demand 或 Spot；
- 让 Kubernetes 的 label、taint、toleration、anti-affinity 和 PDB 明确表达故障域。

本次验证不代表现有 EBS-first 方案已经具备完整 Spot 自动恢复。数据节点未来可以
引入 Spot，但在中断事件消费、快照疏散、`needs_reschedule` 消费和跨 AZ 恢复完成前，
不能把“可创建 Spot 节点”当作“生产可安全使用 Spot”。

## 2. 实测拓扑

```text
EKS claude-sbx
├── system_arm64（On-Demand，2 × m7g.large）
│   ├── sandbox-control-plane × 2（跨节点 anti-affinity）
│   ├── LiteLLM
│   └── CoreDNS
└── sandbox_amd64（On-Demand，1 × i7i.8xlarge）
    └── node-agent → Firecracker microVM
```

| 节点 | 实例 | AZ | 架构 | 角色 |
|---|---|---|---|---|
| `ip-10-0-102-63` | `m7g.large` | `us-east-1b` | arm64 | system |
| `ip-10-0-103-113` | `m7g.large` | `us-east-1c` | arm64 | system |
| `ip-10-0-103-247` | `i7i.8xlarge` | `us-east-1c` | amd64 | sandbox data |

system 节点标签为 `role=system,workload-tier=system`。数据节点标签为
`role=sandbox,sandbox=true,workload-tier=data`，并带
`dedicated=sandbox:NoSchedule` taint。

## 4. 调度隔离验证

| 验证项 | 结果 |
|---|---|
| node-agent 仅在 `sandbox=true` 节点 | PASS |
| 控制面两个副本分别落在两个 system 节点 | PASS |
| LiteLLM 运行在 system 节点 | PASS |
| CoreDNS 仅运行在 system 节点 | PASS |
| 无特殊 toleration 的普通 Pod 落到 system 节点 | PASS |
| sandbox taint 阻止普通工作负载进入数据节点 | PASS |

`FC_NODES` fallback 只从 `sandbox=true` 节点生成，避免控制面把 system 节点误当作
Firecracker 宿主。正常运行时仍优先使用 DynamoDB 节点心跳注册表。

## 5. 异构镜像与凭据

本次使用两种平台分别构建：

- 控制面：`linux/arm64`，运行在 Graviton system 节点；
- node-agent：`linux/amd64`，运行在 i7i 数据节点；
- min-rootfs：`linux/amd64`。

构建脚本会检查实际镜像架构，防止 Docker builder 静默忽略 `--platform`。
node-agent 镜像不再 `COPY` SSH 私钥；实际镜像检查确认不存在
`/root/.ssh/id_ed25519`。exec 主通道为 vsock，如确需 SSH fallback，应在运行时通过
Kubernetes Secret 只读挂载。

## 6. Firecracker E2E

仓库 `scripts/e2e_test.sh` 全部通过，覆盖：

- health / capabilities；
- create / wait / get / list / idempotency / locate；
- vsock exec；
- suspend / resume；
- resume 后再次 exec，并读取 suspend 前写入的状态；
- destroy；
- 无鉴权请求返回 `401`。

本次测试发现旧脚本只验证 resume 后 `state=running`，无法证明 guest 与 vsock
真正可用。严格复测暴露出 warm claim 沙盒在第二次 suspend/resume 后 exec 失联：
快照中的 vsock UDS 仍绑定原 warm sandbox 路径，而 resume 代码错误地按当前
`snap_dir` 推测 symlink 目标。

修复后，`node-agent/main.py` 直接从快照提取权威 vsock UDS 路径，并重建
`real_id/v.sock -> warm_id/v.sock`。E2E 也增加 post-resume exec 与状态保留断言。

严格 2-vCPU 验证：

```json
{
  "before": "x86_64\n2\nresume-proof-20260811",
  "restore_time_s": "10.1483",
  "net_fix_ok": true,
  "after": "x86_64\n2\nresume-proof-20260811"
}
```

## 7. LiteLLM 与控制面高可用

LiteLLM 通过 IRSA 成功调用真实 Amazon Bedrock：

```json
{
  "health": {"status": "healthy", "db": "Not connected"},
  "models": ["claude-opus-4-8", "claude-sonnet-4-6", "claude-haiku-4-5"],
  "completion": "litellm-ok"
}
```

控制面故障转移测试中，主动删除当前 leader Pod：

- 集群内连续 `120/120` 次 Service 请求成功；
- replacement Pod 恢复 Ready；
- DynamoDB leader lock owner 转移到新 Pod。

这证明节点池分离不仅是调度配置：数据节点保持不变时，控制面单 Pod 故障可以由另一
个 system 节点接管。

## 8. Spot 边界

推荐的生产池划分：

| 节点池 | 采购模型 | 工作负载 |
|---|---|---|
| system | **On-Demand** | 控制面、LiteLLM、Ingress、CoreDNS、Karpenter |
| sandbox-protected | On-Demand | 活跃、不可中断或正在疏散的 microVM |
| sandbox-spot | Spot | 满足恢复条件的空闲/可中断 microVM |

system 节点不要使用 Spot。当前仓库的 EBS-first 快照模型仍绑定单 AZ，且 Spot
中断后的自动跨节点恢复链路尚未闭环；因此本次 Terraform 仍将 sandbox 数据节点设为
On-Demand。Spot 应作为后续独立阶段实施和压测。

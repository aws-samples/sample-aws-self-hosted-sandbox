## 1. 结论摘要

| 维度 | 客户其他云的经验值 | r8i.8xlarge + EKS 实测 | 结论 |
|---|---|---|---|
| vCPU 超分 | 1:60 | **硬上限约 1:10**：同时运行的 guest vCPU 超过约 290～320 个，VM 会被 `KVM_EXIT_FAIL_ENTRY` 随机杀死 | ❌ 嵌套虚拟化下达不到 |
| CPU 超分（体验） | — | 同时活跃的 vCPU ≤ 宿主线程数 2 倍时，交互 p99 ≤ 22 ms；8 倍时 p99 4.9 s 并出现超时 | ⚠️ 按「活跃比例」规划容量，不能只看配置比 |
| 内存超分（配置） | 1:6 | 256 个 VM × 6 GiB = 1536 GiB 配置内存，全部正常运行 | ✅ 可以做到 |
| 内存超分（实际使用超过物理内存） | — | 无保护：**整节点 livelock，NotReady 26 分钟**<br>加 `sbx.slice` 后：只杀单个 VM，节点始终 Ready | ⚠️ 必须同时有 slice 保护和准入控制 |
| KSM | — | AL2023 内核没有编进 KSM | ❌ |
| 磁盘共享 | 共享 / 超分 | rootfs 改为同盘 reflink 后，每个沙盒新增占盘接近 0；XFS 上的 Full base 快照按配置内存全额写满 | ✅ rootfs 可以；⚠️ base 快照是主要的磁盘消耗 |
| **Spot 120 s 快照（XFS/EBS）** | 「十几台」 | 优化后 **60 个 2 GiB 沙盒（81 GiB 脏页）102.5 s 完成**，恢复抽检内存 sha256 全部一致 | ✅ 远超十几台；瓶颈是实例 EBS 带宽 |
| **FIS 真实中断** | — | 20/20 在通知窗口内 checkpoint 完成，状态 EBS 保留成功，standby 接管后 20/20 恢复为 running | ✅ 主链路通过（中途修了 2 个阻断 bug，见 §4） |
| ZFS（压缩） | 客户称验证成功 | 吞吐潜力 +40%（1004 MiB/s，压缩 1.82 倍），但**现有 Diff 合并方式在 ZFS 上会静默损坏内存**；用正确配置（recordsize=4K）时只有 302 MiB/s | ⚠️ 必须改合并方式才能用 |
| Lustre | — | 同样存在静默损坏内存的问题；和 EBS 混合写入也没有带来增益 | ❌ 现有设计下不推荐 |
| WEKA | — | 只做了文档调研（至少 6 台后端 + 商业授权；客户端列表里没有 r8i；Augmented Memory Grid 面向 GPU KV cache） | ❌ 不适合这个场景 |

## 2. 超分测试

### 2.1 vCPU 上限（嵌套虚拟化）

- **现象**：VM 启动正常，若干秒到几分钟后 vCPU 收到 `KVM_EXIT_FAIL_ENTRY`（hardware entry failure reason 7），firecracker 随即退出；宿主 dmesg 刷 `set kvm_intel.dump_invalid_vmcs=1`。node-agent **感知不到 VM 已经退出**，仍然记为 running。
- **阈值**（`bench-results/t0-threshold.log`）：

| VM 规格 | 稳定档 | 开始失败的点 | 存活上限 |
|---|---|---|---|
| 2 vCPU | 128 个 VM（256 vCPU），0 失败 | 约 158 个 VM（约 316 vCPU） | 约 213 个 VM |
| 1 vCPU | 224 个 VM（224 vCPU），0 失败 | 约 286 个 VM | 约 316～331 个 VM |

- 和 vCPU 总数有关，和 CPU 负载无关：128 个 VM 全速满载（load 69）也是 0 失败。低密度对照（8 个 VM，观察 5 分钟）同样 0 失败。
- 宿主侧把 `kvm_intel` 的 `enable_apicv` 和 `pml` 关掉也**无效**。判断是 Nitro L0 对嵌套 VMCS 的限制。
- **建议**：r8i.8xlarge 上 guest vCPU 总数不超过约 256（1:8）。要做更高的 vCPU 超分，需要在 metal 机型（没有嵌套虚拟化）上验证，或者确认这个上限是否随实例规格线性增长。这两项都没测。

### 2.2 CPU 争用（256 个 VM × 1 vCPU；空闲 VM 往返延迟在 Pod 内直连 vsock 测得）

| 同时忙碌的 VM | 单 VM 吞吐（独占时 28,189 次/s） | 空闲 VM 延迟 p50 / p99 / max |
|---|---|---|
| 1 | 100% | 3.7 / 4.3 / 5.7 ms |
| 16 | 100% | 4.1 / 6.1 / 7.0 ms |
| 32（= 宿主 vCPU 数） | 65%（超线程共享物理核） | 4.3 / 16 / 25 ms |
| 64（2 倍） | 33% | 4.3 / 22 / 25 ms |
| 128（4 倍） | 17% | 4.3 / 62 / 129 ms |
| 256（8 倍） | 约 10% | 30 ms / **4.9 s** / 7.0 s，1/8 的探测超时 |

### 2.3 内存

- **空闲开销**：2 GiB 的 VM 约 102 MiB RSS，6 GiB 的 VM 约 251 MiB。配置内存的约 1.56% 会被 guest 的 `struct page` 元数据真实占用。
- **1:6 配置**（256 × 6 GiB）：空闲时宿主只用了 64 GiB 内存、约 2% CPU。
- **实际使用逐级加压**：

| 阶段 | 无保护（节点 A） | `sbx.slice` MemoryMax=88%（节点 A'） |
|---|---|---|
| VM 实际 RSS 197 GiB | 正常 | 正常 |
| 约 231 GiB | 正常（只剩 12 GiB） | slice 触顶，cgroup OOM 杀掉 16 个 VM，**节点 Ready** |
| 超过物理内存 | **整机颠簸**，kubelet 和 SSM 失联，NotReady 26 分钟，期间只 OOM 掉 2 个 VM，最后只能重启，节点上 VM 全部丢失 | 累计杀掉 48 → 88 个 VM，kubelet 始终 active，**节点始终 Ready** |

- **仍缺失**：按已提交内存做准入控制；node-agent 检测 VMM 退出后回写状态；balloon free page reporting 的回收效果；zram/zswap 兜底。后两项还没测。

### 2.4 磁盘

- rootfs 模板本身是稀疏文件（表观 2 GiB，实占 254 MiB）。改为在状态盘上缓存模板、每个沙盒从缓存 reflink 之后，960 个沙盒的状态盘总占用只从 2.8 GiB 涨到 6.1 GiB。
- XFS 上，2 GiB 的 VM 打一次 Full base 快照要实写 2 GiB、耗时约 8.3 s。ZFS 开压缩时全零页直接存成空洞，40 个 VM 的 base 只用了 27.7 s，XFS 是 85.8 s。

## 3. Spot 120 秒快照测试

测试方法（`scripts/bench/spot_bench.py`）：
- 单节点上建 N 个 2 GiB / 1 vCPU 的沙盒。
- 先做 Full base 快照，然后用 memtouch 在每个 guest 里写 1200 MiB 的 **mixed 内容**：真实文件内容，掺 20% 随机页。注意，codex 9 月那轮测试的脏页是全零填充。
- 宿主 `sync` 静默后，调用 `/reclaim/simulate`，走**真实的并发 checkpoint 路径**：并发度 8，截止时间 112 s。
- 抽样 resume 3 个 VM，比对 guest 内存的 sha256（h1 = h2 才算保真）。

每个沙盒的 Diff 约 1.35 GiB，其中 1.2 GiB 来自 memtouch，其余是 Python 进程和页缓存。

| 场景 | 沙盒数 | 成功 | 写盘墙钟 | 逻辑数据 | 实际落盘 | 有效速率 | 恢复抽检 |
|---|---:|---:|---:|---:|---:|---:|---|
| XFS，优化前 | 40 | 39 | 123.0 s | 54.1 GiB | 54.1 GiB | 451 MiB/s | ✅ 一致 |
| **XFS，优化后**（base 哈希预热） | 40 | **40** | **77.1 s** | 54.1 GiB | 54.1 GiB | **719 MiB/s** | ✅ 一致 |
| **XFS，优化后** | **60** | **60** | **102.5 s** | 81.2 GiB | 81.2 GiB | **811 MiB/s** | ✅ 一致 |
| ZFS lz4，rs=4K（数据正确的配置） | 40 | 27 | 123.9 s | 36.5 GiB | 37.2 GiB | 302 MiB/s | ✅ 一致 |
| ZFS lz4，rs=1M（**仅看吞吐，数据会损坏**） | 40 | 40 | 56.9 s | 55.8 GiB | 30.6 GiB | 1004 MiB/s | ❌ 不可用 |
| XFS 40 + Lustre 40 混合 | 80 | 56 | 117.0 s | 90.1 GiB | 79.0 GiB | 约 691 MiB/s（按实际落盘算） | XFS 部分 ✅ |

### 3.1 关键发现

1. **XFS 在 r8i.8xlarge 上 120 s 内可以保存约 60 个（约 81 GiB）真实内容的脏页沙盒**。瓶颈是实例级 EBS 带宽（1,250 MB/s），卷本身配置的 40k IOPS / 2,000 MiB/s 用不满。这和 codex 9/3 报告的「71 个（全零脏页）」处在同一个量级。客户说的「十几台」，更可能是当时配置的状态卷 IOPS 太低（4,000），或者每个沙盒的脏页更大。容量可以按下式估算：**N ≈ 90 s × 0.8 GB/s ÷ 每沙盒脏页量**。
2. **优化：base 快照哈希预热（已提交，+59%）**。优化前，checkpoint 期间的完整性校验会把 dense base 从 EBS 冷读一遍：读流量 200～630 MiB/s，和写入争抢同一份实例带宽，`InstanceEBSThroughputExceededCheck=1`。改为在 base 写完时就把哈希算进缓存之后，校验逻辑一行不变，40 个沙盒从 39/40、123 s 提升到 40/40、77 s。
3. **ZFS：节省带宽确有其事，但在现有设计下会静默损坏内存**。
   - node-agent 合并 Diff 时，依靠 `SEEK_DATA/SEEK_HOLE` 判断哪些页被写过。这要求文件系统的空洞粒度精确到 4 KiB 页。
   - ZFS 的空洞粒度等于 recordsize：一个 1 MiB 的 record 里只要写了一页，整个 record 都会被当成「有数据」，其中没写过的页以零覆盖到 base 上。
   - 实测：rs=1M 时，不管 `compression=off` 还是 `lz4`，resume 之后 guest 都会立即 triple fault；rs=4K 时恢复正确，但吞吐跌到 302 MiB/s，而且 4K record 基本压缩不了。
   - **要让 ZFS 真正可用**，需要把合并方式改成「先 block-clone 一份 base，让 Firecracker 把 Diff 原地写进去」（Firecracker 本身支持这种用法），去掉对 `SEEK_DATA` 的依赖。改完后 rs=1M + lz4 的吞吐潜力是 **1004 MiB/s，比 XFS 高约 40%**，落盘量减少 45%。之后再用 `zfs send -c` 异步增量同步到 S3。
   - 客户说的「ZFS 验证成功」，建议问清楚两点：是不是用了 Full 快照（不走 Diff 合并）？有没有做恢复后的内存一致性校验？
4. **Lustre：同样会静默损坏内存，而且混合写入没有收益**。Lustre 客户端的 `SEEK_DATA` 不报告空洞，结果和 ZFS 一样。混合布局只完成了 56/80：Lustre 这一路单 VM 耗时更长，和 EBS 共用同一个并发度为 8 的 checkpoint 队列，把整体都拖慢了。理论上网卡（15 Gbps）和 EBS 的带宽可以叠加，但要做到，需要按存储路径分别设置并发，并且合并方式要和文件系统无关。
5. **Spot 容量本身就是风险**：r8i.8xlarge（以及 r8i 全系列）在 use1-az2 的 Spot 放置评分只有 **1 / 10**，Spot 节点组 `CREATE_FAILED`，最后改用 m8i.4xlarge（评分 3）才拿到容量。方案为了接管 EBS 把 Spot 池钉在单个 AZ，就要承受这个 AZ 的容量波动。

### 3.2 FIS 真实中断端到端（实验 `EXPDqCauAQ4LjThEkJ`）

配置：Spot m8i.4xlarge，20 个沙盒 × 2 GiB，每个 1200 MiB 脏页；standby 为按需 m8i.4xlarge。

| 阶段 | 结果 |
|---|---|
| IMDS 检测到中断通知 → checkpoint 全部完成 | 从发出中断起 **64.6 s** |
| 并发 checkpoint（并发 8） | **20/20**，写盘 36.2 s，24.0 GiB，679 MiB/s |
| 状态 EBS 保留（DeleteOnTermination 改为 false 并回读确认） | 1.95 s，实例终止后卷处于 available ✅ |
| standby 认领 → 挂卷 → 恢复 | 修复 2 个阻断问题后，**20/20 恢复为 running**，约 40 s |
| 自动迁回 Spot（OD 回收） | ❌ 卷交接阶段循环失败，沙盒再次离线（见 §4 第 9 项） |

恢复后的内存标记校验没有完成：脚本在等恢复时超时了（恢复功能当时被关着），之后沙盒又被迁回流程打到了离线状态。要补这一项，需要关掉 OD 回收后重跑一次（见 §7）。

## 4. 真机发现并修复的问题

1. phase3 的 user-data 超过 EC2 16 KB 上限 → helper 改为从 S3 下载并做 sha256 校验（16,376 → 8,988 字节）。
2. jailer 的 `--new-pid-ns` 和 systemd `Type=exec` 冲突，所有 VM 一启动就被 SIGKILL → 去掉该参数。
3. jailer 降权后快照目录归 root，**所有快照报 EACCES**，Spot checkpoint 会 100% 失败 → 快照目录交给 VM 的运行 uid。
4. `tap_idx` 超过 255 后 guest 无 IPv4 → 映射到 172.19.0.0/16。
5. rootfs 跨文件系统时 reflink 失效 → 在状态盘上缓存模板。
6. 内存超分时整机 livelock → 引入 `sbx.slice`（MemoryMax=88%）。
7. checkpoint 时冷读 base 抢占 EBS 带宽 → base 写完即预热哈希（+59%）。
8. `sbx-state-volume` 用 `findmnt --target` 判断挂载，把根盘误判成「已挂载」，**standby 接管 100% 失败** → 改为 `--mountpoint`。
9. **未修复**：OD 回收（把沙盒从按需 standby 迁回新的 Spot 节点）在卷交接阶段循环报 `spot_recovery_od_recycle_failed`，已经恢复的沙盒又变成离线。建议先关闭这个功能（`spot_recovery_od_recycle_enabled=false`），再单独排查。
10. **未修复**：Diff 合并依赖 `SEEK_DATA`，在 ZFS 和 Lustre 上会静默损坏内存（见 §3.1）。在合并方式改掉之前，状态盘只能用 XFS 或 ext4。

## 5. 测试有效性说明

测试过程中，同一账号、同一台机器上**另一个会话在并行操作同一个集群**：
- 在节点 B' 上创建了 70 个 `xa-*` 沙盒；
- 删掉了节点 A' 上本测试的 256 个 VM；
- 改掉了本测试 stage2 参数文件里的 `spot_recovery_enabled`，导致 FIS 测试刚开始时恢复功能是关着的。

为此：
- Spot 容量测试全部改在只有本测试 VM 的节点上进行，触发 checkpoint 前会检查节点上有没有其他人的沙盒（`spot_bench.py`）。
- 15:00 那次混入了对方 VM 的 ZFS 测试作废。
- 内存 D 阶段只拿到了累计 OOM 计数（88）。

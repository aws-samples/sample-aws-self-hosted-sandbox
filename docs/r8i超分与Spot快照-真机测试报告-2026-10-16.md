## 1. 结论摘要

| 维度 | 客户其他云的经验值 | r8i.8xlarge + EKS 实测 | 结论 |
|---|---|---|---|
| vCPU 超分 | 1:60 | 默认调度下**硬上限约 1:9**：同时运行的 guest vCPU 超过约 288 个，VM 就会被 `KVM_EXIT_FAIL_ENTRY` 随机杀死。**把每个 VM 的 vCPU 线程绑定到单个宿主 CPU 之后（§12），同一台嵌套 r8i.8xlarge 上 1920 个 VM（60:1）0 失败**。r8i.metal-48xl 不绑核时 11520 个 vCPU（60:1）0 失败 | ✅ **嵌套机型绑核后做到 1:60**（空闲 VM，待完整链路验证）；✅ metal 不需要绑核 |

## 2. 超分测试

### 2.1 vCPU 上限：嵌套虚拟化下的硬限制

**现象**：VM 能正常启动，但若干秒到几分钟后 vCPU 收到 `KVM_EXIT_FAIL_ENTRY`（hardware entry failure reason 7），firecracker 随即退出。宿主 dmesg 里不断刷 `set kvm_intel.dump_invalid_vmcs=1`。**node-agent 感知不到 VM 已经退出**，仍然把它记为 running。

**EKS 节点上的阈值**（`bench-results/t0-threshold.log`）：

| VM 规格 | 稳定档（0 失败） | 开始失败的点 | 存活上限 |
|---|---|---|---|
| 2 vCPU | 128 个 VM（256 vCPU） | 约 158 个 VM（约 316 vCPU） | 约 213 个 VM |
| 1 vCPU | 224 个 VM | 288 个 VM | 316～331 个 VM |

- 失败与 **vCPU 总数**有关，与 CPU 负载无关：128 个 VM 全速满载（load 69）时也是 0 失败；低密度对照（8 个 VM，观察 5 分钟）同样 0 失败。
- 在宿主上把 `kvm_intel` 的 `enable_apicv` 和 `pml` 关掉也**无效**，上限仍是约 330。

**独立 EC2 对照**（不经过 EKS，宿主内核 6.18，每个 VM 1 vCPU / 128 MiB，`scripts/bench/nested-cap-probe.sh`，原始结果见 `bench-results/t0-nested-cap-probe.md`）：

| 机型 | 宿主 vCPU | 虚拟化 | 0 失败的最高档 | 首次失败 |
|---|---:|---|---:|---|
| r8i.8xlarge | 32 | 嵌套 | 256 | 288 个时失败 1 个，320 个时失败 26 个 |
| r8i.16xlarge | 64 | 嵌套 | 512 | 576 个时失败 11 个，640 个时失败 36 个 |
| **r8i.metal-48xl** | 192 | **无（裸金属）** | **3072（16:1）** | 无 |
| **r8i.metal-48xl**（96 MiB/VM） | 192 | 无 | **11520（60:1）**：4096 / 6144 / 8192 / 11520 四档全部存活，load 7.0，剩余可用内存 661 GiB | 无 |

**结论**：
- 这个上限**由 Nitro 嵌套虚拟化决定**，与 EKS 和宿主内核版本都无关，**每个宿主 vCPU 大约只能承载 8～9 个 guest vCPU**。r8i.8xlarge 上做不到 1:60 的 CPU 超分，生产环境的硬上限建议定在 1:8（256 个 guest vCPU）。
- 裸金属没有这个限制。要做 1:60，**只能用 metal 机型**，或者把单个 VM 的 vCPU 配置收紧，用按活跃度动态分配的方式替代按配置值超分。
- 代价是 metal 机型启动约 10 分钟，而且规格很大（192 vCPU / 1.5 TiB），单节点故障域也随之变大。

> **2026-10-19 更新**：上述上限只在「vCPU 线程可以在宿主 CPU 之间自由迁移」时成立。**每个 VM 绑定到单个宿主 CPU 后，嵌套 r8i.8xlarge 上 1920 个 VM（60:1）0 失败**，详见 §12。

### 2.2 CPU 争用

256 个 VM × 1 vCPU。空闲 VM 的往返延迟在 node-agent Pod 内直连 vsock 测得，排除了跨地域网络的影响（`bench-results/t1-cpu.log`）：

| 同时忙碌的 VM | 单 VM 吞吐（独占时 28,189 次/s） | 空闲 VM 延迟 p50 / p99 / max |
|---|---|---|
| 1 | 100% | 3.7 / 4.3 / 5.7 ms |
| 16 | 100% | 4.1 / 6.1 / 7.0 ms |
| 32（= 宿主 vCPU 数） | 65%（超线程共享物理核） | 4.3 / 16 / 25 ms |
| 64（2 倍） | 33% | 4.3 / 22 / 25 ms |
| 128（4 倍） | 17% | 4.3 / 62 / 129 ms |
| 256（8 倍） | 约 10% | 30 ms / **4.9 s** / 7.0 s，8 次探测中有 1 次超时 |

**结论**：CPU 超分能不能成立，取决于**同时活跃的 vCPU 数**，配置比例不是关键。空闲的沙盒几乎不占 CPU：256 个空闲 VM 合计只占宿主约 1.9%。

### 2.3 内存

**空闲开销**：2 GiB 的 VM 约 102 MiB RSS，6 GiB 的 VM 约 251 MiB。配置内存的约 1.56% 会被 guest 内核的 `struct page` 元数据真实占用，所以配置值并不是零成本的。

**1:6 配置**（256 × 6 GiB = 1536 GiB）：全部正常运行，宿主只用了 64 GiB 内存、约 2% CPU。

**实际使用逐级加压**（`bench-results/t1-mem.log`、`t1-mem-slice.log`、`t1-zram.jsonl`）：

| 阶段 | 无保护（节点 A） | `sbx.slice` MemoryMax=88%（节点 A'） | `sbx.slice` + 64 GiB zram（zstd，节点 A''） |
|---|---|---|---|
| VM 实际 RSS 约 197 GiB | 正常 | 正常 | — |
| 约 231 GiB | 正常，只剩 12 GiB | slice 触顶，cgroup OOM 杀掉 16 个 VM，**节点 Ready** | slice 停在 217 GiB，**19 GiB 换出到 zram，0 次 OOM**，200/200 存活 |
| 超过物理内存 | **整机颠簸**：kubelet 和 SSM 全部失联，**NotReady 26 分钟**，期间只 OOM 掉 2 个 VM，最后只能重启，节点上 VM 全部丢失 | 累计杀掉 48 → 88 个 VM，kubelet 始终 active，**节点始终 Ready** | — |
| 交互延迟（vsock 往返） | — | — | p50 3.8 → 14.4 ms，p99 4.4 → 40 ms，max 50 ms，0 次失败 |

- zram 的压缩效果（`/sys/block/zram0/mm_stat`）：换出 20.9 GB 原始数据，只占 **0.81 GB** 物理内存，其中 6.9 GiB 是全零/同值页。这么高的压缩比和测试内容高度相关（memtouch 的 mixed 模式里，80% 是 Python 源码这类文本），真实业务内存的压缩比必须用实际负载测；随机内容基本压不动。
- 注意：kubelet 默认启用 `failSwapOn`。本次 zram 是在 kubelet 启动之后才开启的；生产环境需要在 kubelet 配置里显式允许 swap，或者确认 kubelet 重启后的行为。

**balloon free page reporting（FPR）**（`bench-results/t1-balloon.jsonl`）：

| | 空闲 | guest 写入 3000 MiB 后 | guest 释放 10 s 后 | 60 s 后 |
|---|---|---|---|---|
| 不开 FPR | 220 MiB | 3226 MiB | **3230 MiB**（不回落） | 3230 MiB |
| 开 FPR | 218 MiB | 3226 MiB | **240 MiB** | 240 MiB |

不开 FPR 时，每个沙盒的宿主 RSS 只涨不降，最终都会停在它历史上的峰值，内存超分会随时间逐渐失效。**现已默认开启**：stage2 变量 `balloon_free_page_reporting`，默认值 true（见 §10）。

### 2.4 磁盘

- rootfs 模板本身是稀疏文件：表观 2 GiB，实际只占 254 MiB。旧代码跨文件系统做 `cp --reflink=auto`，会退化成实拷，每个沙盒约 254 MiB。改为在状态盘上缓存一份模板、每个沙盒从缓存 reflink 之后，**960 个沙盒的状态盘总占用只从 2.82 GiB 涨到 6.09 GiB**，平均每个沙盒约 3.5 MiB（`t1-density.jsonl`）。
- **base 快照是磁盘上真正的大头**：XFS 上，2 GiB 的 VM 打一次 Full base 要实写 2 GiB，60 个 VM 需要 133.6 s。ZFS 开压缩时全零页直接存成空洞，60 个只要 19.6 s，100 个 35.9 s。

### 2.5 EKS 环境下的具体问题

| # | 问题 | 现象（真机） | 处置 |
|---|---|---|---|
| E1 | VMM 是 node-agent Pod 的子进程（9/2 线上部署） | Pod 重启会杀掉全部 VM；VM 的内存记在 Pod 名下，会触发 kubelet 驱逐 | codex 已改为宿主 systemd 服务；本轮验证 **Pod 重建 22 s 期间 VM 持续运行**，新 Pod 自动接管 |
| E2 | VMM 不在 kubepods 下，kubelet 看不到这部分内存 | 内存 livelock 时，kubelet 的驱逐机制完全没有起作用 | 引入 `sbx.slice` 设定内存上限；建议同时设置 kubelet 的 `systemReserved`，把 slice 那部分预留出来 |
| E3 | 单 AZ 子网 IP 耗尽 | VPC CNI 让每台大节点预占 50 个 IP，7 台节点就把 /24 子网耗尽，节点组滚动报 `NodeCreationFailure` | vpc-cni 设置 `WARM_IP_TARGET=2`、`MINIMUM_IP_TARGET=4`，空闲 IP 从 0 恢复到 215 |
| E4 | 托管节点组的 user-data 有 16 KB 上限 | 内嵌 helper 后 apply 直接失败 | helper 改为从 S3 拉取并做 sha256 校验，user-data 降到 8,988 B |
| E5 | 启动模板里的 helper sha 和 S3 不同步 | 新节点（standby）因校验失败缺少 helper，node-agent 一直 not ready | phase3 必须和 helper 一起 apply；测试栈也要随之刷新 |
| E6 | 控制面调度不感知容量 | `_pick_node` 只看空闲内存，没有 vCPU 和准入控制 | 待实现：按 vCPU 上限（嵌套机型约 1:8）和已提交内存做准入 |
| E7 | node-agent 不检测 VMM 退出 | 被 OOM 或 FAIL_ENTRY 杀掉的 VM 一直显示 running | 待实现：监听 systemd unit 的退出，回写状态，并从最近一次快照拉起 |

## 3. Spot 120 秒快照测试

测试方法（`scripts/bench/spot_bench.py`）：
- 单个 r8i.8xlarge 节点上建 N 个 2 GiB / 1 vCPU 的沙盒。
- 先做 Full base 快照，然后用 memtouch 在每个 guest 里写入 1200 MiB 脏页。内容分两种：**mixed**（真实文件内容掺 20% 随机页）和 **random**（不可压缩）。注意，codex 9 月那轮用的是全零填充。
- 宿主 `sync` 静默后，调用 `/reclaim/simulate`，走**真实的并发 checkpoint 路径**：并发度 8，截止时间 112 s（120 s 减去 8 s 提交预留）。
- 抽样 resume 3 个 VM，比对 guest 内存的 sha256（h1 = h2 才算保真）。
- 每个沙盒的 Diff 约 1.35 GiB（在 XFS 上实测），其中 1.2 GiB 来自 memtouch，其余是 Python 进程和页缓存。

结果（`bench-results/t2-spot.jsonl`）：

| 存储 | 内容 | 沙盒数 | 成功 | 写盘墙钟 | 单 VM p99 | base 用时 | 恢复抽检 |
|---|---|---:|---:|---:|---:|---:|---|
| XFS，优化前 | mixed | 40 | 39 | 123.0 s | 29.1 s | 85.8 s | ✅ |
| XFS，base 哈希预热后 | mixed | 40 | 40 | 77.1 s | 17.6 s | 94.1 s | ✅ |
| **XFS** | mixed | **60** | **60** | **102.5 s** | 17.5 s | 133.6 s | ✅ |
| ZFS lz4 rs=1M，旧的稀疏合并方式 | mixed | 4 | 4 | — | — | — | ❌ **resume 后内存损坏** |
| ZFS lz4 rs=4K，旧方式（数据正确） | mixed | 40 | 27 | 123.9 s | 51.7 s | 85.8 s | ✅ |
| **ZFS lz4 rs=1M，原地合并（本轮）** | mixed | 60 | 60 | **61.5 s** | 12.6 s | 19.6 s | ✅ |
| **ZFS lz4 rs=1M，原地合并** | mixed | 80 | 80 | 71.6 s | 10.5 s | 26.8 s | ✅ |
| **ZFS lz4 rs=1M，原地合并** | mixed | **100** | **100** | **91.6 s** | 11.9 s | 35.9 s | ✅ |
| ZFS lz4 rs=1M，原地合并 | mixed | 120 | 116 | 114.4 s（撞上截止时间） | 13.6 s | 38.7 s | ✅ |
| **ZFS lz4 rs=1M，原地合并** | **random** | 60 | 60 | **76.0 s** | 14.3 s | 19.5 s | ✅ |
| XFS 40 + Lustre 40 混合 | mixed | 80 | 56 | 117.0 s | 24.3 s | 228.2 s | XFS 部分 ✅ |

### 3.1 关键发现

1. **XFS 在 r8i.8xlarge 上 120 s 内可以保存约 60 个沙盒（约 81 GiB 脏页）**。瓶颈是实例级 EBS 带宽（1,250 MB/s），卷本身配置的 40k IOPS / 2,000 MiB/s 用不满。客户说的「只能十几台」，更可能是状态卷 IOPS 太低（4,000，平均 I/O 约 227 KiB 时会先撞 IOPS 上限），或者每个沙盒的脏页更大。容量可以按下式估算：**N ≈ 90 s × 有效写入带宽 ÷ 每沙盒脏页量**。
2. **base 哈希预热（+59%）**：优化前，checkpoint 期间的完整性校验会把 dense base 从 EBS 冷读一遍，和写入抢同一份实例带宽，导致 `InstanceEBSThroughputExceededCheck=1`。改为在 base 写完时就把哈希算进缓存之后，40 个沙盒从 39/40、123 s 提升到 40/40、77 s。
3. **ZFS：旧的合并方式会静默损坏内存。本轮已修复，修复后容量是 XFS 的 1.7 倍。**
   - **根因**：node-agent 用 `SEEK_DATA/SEEK_HOLE` 判断 Diff 里哪些页被写过，这要求文件系统的空洞粒度精确到 4 KiB。ZFS 的空洞粒度等于 recordsize：一个 1 MiB 的 record 里只要写了一页，整个 record 都会被当成「有数据」，没写过的页以零覆盖到 base 上，resume 之后 guest 立即 triple fault。Lustre 也有同样的问题。
   - **修复**（`SNAPSHOT_DIFF_MODE=auto`，在 ZFS 上自动启用）：suspend 时先用 `cp --reflink=always` 把 base block-clone 成同尺寸的 `vm.mem`（O(1)，不占额外空间），再让 Firecracker 把 Diff **原地写进去**。Firecracker 本身支持对已存在且尺寸匹配的 mem 文件做原地合并。写完的文件就是完整内存镜像，resume 直接 load，不再依赖 `SEEK_DATA`。内存镜像的完整性改由 ZFS 端到端块校验保证（默认 fletcher4，可以设成 sha256），关键路径上不再做 sha256 冷读。
   - **效果**：mixed 内容下 100 个 VM 用时 91.6 s（XFS 60 个要 102.5 s），**恢复后内存 sha256 全部一致**。即使是不可压缩的 random 内容，60 个也只要 76 s，比 XFS 快约 26%：一方面 ZFS 的事务组把零散的脏页写聚合成了大块顺序写，另一方面关键路径上省掉了两遍 sha256。
   - **代价**：
     - 宿主 system CPU 从约 2～3% 涨到 13～17%，大约多用 5 个 vCPU 做压缩。
     - ZFS 卷的物理写入峰值约 1,043 MiB/s（CloudWatch 1 分钟粒度），说明**瓶颈仍然是实例 EBS 带宽**，ZFS 的收益来自压缩和更高效的写入。
     - AL2023 没有官方的 ZFS 包，需要源码编译（32 核约 1 分钟），并且应该烤进自定义 AMI。内核升级时要重新编译 kmod。
   - 客户说的「ZFS 验证成功」，建议问清楚两点：是不是只用了 Full 快照（不走 Diff 合并）？有没有做恢复后的内存一致性校验？
4. **Lustre 不推荐**：它的客户端不报告空洞，同时也不支持 reflink，所以原地合并在 Lustre 上会退回到旧方式，依然会损坏数据。混合布局只完成了 56/80：Lustre 这一路单 VM 耗时更长，和 EBS 共用同一个并发度为 8 的队列，把整体都拖慢了。理论上网卡（15 Gbps）和 EBS（10 Gbps）的带宽可以叠加，但要做到，需要按存储路径分别设置并发，并且合并方式要和文件系统无关。
5. **Spot 容量本身就是风险**：r8i 全系列在 use1-az2 的 Spot 放置评分只有 1/10。方案为了接管 EBS 把 Spot 池钉在单个 AZ，就要承受这个 AZ 的容量波动。

### 3.2 FIS 真实中断端到端（实验 `EXPbY5Dt3RwxGtSJwk`，`bench-results/t2-fis-e2e-20-rerun.json`）

配置：Spot m8i.4xlarge，20 个沙盒 × 2 GiB，每个 1200 MiB 脏页，standby 为按需 m8i.4xlarge。Spot 恢复开启，OD 回收关闭。

## 4. 本轮在真机上发现并修复的问题

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | phase3 的 user-data 超过 EC2 16 KB 上限 | 部署失败 | helper 改为从 S3 下载并做 sha256 校验（16,376 → 8,988 B） |

## 5. 给客户的建议

1. **CPU 超分**：r8i.8xlarge（嵌套虚拟化）在默认调度下，guest vCPU 总数的硬上限约 288。**把每个 VM 的 vCPU 线程绑定到单个宿主 CPU 后，实测 60:1 0 失败（§12）**，这是嵌套机型做高超分的前提；绑核落地之前，生产上限仍按 1:8。另一条路是 r8i.metal（实测 11520 个 vCPU，即 60:1，不绑核也 0 失败），要评估 metal 冷启动约 10 分钟和单节点故障域变大的代价。无论哪种机型，都要按**同时活跃的 vCPU ≤ 宿主线程数 2 倍**来规划交互型负载。
2. **内存超分**：1:6 的配置比可以做到，但必须同时具备以下四项：
   ① `sbx.slice` 设内存上限；
   ② zram 兜底；
   ③ balloon free page reporting；
   ④ 控制面按「实际 RSS + 已提交内存」做准入控制。
   缺了前两项，一次超限就可能让整台节点失联。
3. **磁盘**：rootfs 用同盘 reflink 共享（本轮已实现）；base 和 Diff 快照放到 ZFS（lz4）上，可以节省约 40% 的落盘量和带宽。
4. **Spot 快照**：
   - XFS 方案：r8i.8xlarge 每台约 60 个（每个沙盒 1.35 GiB 脏页）。
   - **ZFS + 原地合并方案：每台约 100 个**。
   - 规划时按 `N ≈ 90 s × 0.8～1.4 GB/s ÷ 每沙盒脏页量` 估算，并且要实测客户真实负载的脏页量和压缩比。
   - 状态卷 IOPS 至少配到 40,000，否则会先撞 IOPS 上限。
5. **不推荐**：Lustre（数据正确性问题，而且没有带宽收益）、WEKA（门槛和成本过高，与场景不匹配）。如果需要跨 AZ 容灾，可以在 standby 恢复之后，再用 `zfs send -c` 把快照异步增量同步到 S3。

## 9. E2B 的可借鉴之处（架构对照；其中两项已在 §11 真机验证）

资料来源：E2B 开源 runtime 的架构文档（`e2b-dev/runtime@f9b828e7`，`docs/ARCHITECTURE.md` 中的 Orchestrator 与 Pause/Resume 两节）。下表把它的机制和本轮实测到的瓶颈逐一对照。

| E2B 机制 | 它解决什么问题 | 对应本方案实测到的问题 | 借鉴价值 |
|---|---|---|---|
| **以模板的内存快照作为共享 base**：沙盒从模板 memfile resume 出来，pause 时只导出相对模板的脏页 | 不用为每个沙盒单独写一份 Full 内存 | 每个沙盒创建后要写一份 Full base：XFS 上 60 个要 133.6 s，磁盘按配置内存全额占用 | **高**：省掉 base 这一步，磁盘和 EBS 带宽的占用都大幅下降。前提是所有沙盒都从模板快照 resume 出来，而不是冷启动 |
| **原地 Checkpoint**（pause → 快照 → 原地 resume）+ 分层快照 | 平时就把状态落盘 | 120 s 窗口的容量取决于「距离上一次落盘以来的脏页量」 | **高**：周期性 checkpoint 之后，Spot 通知到来时只需要写最后一段增量。和本轮的 ZFS 原地合并天然契合，每一代都是 base 克隆 + 原地 Diff，多代正确性已经验证 |
| **UFFD 按需分页恢复** + 预取热点页（optimize 阶段记录 resume 时会访问哪些页） | resume 时不读入整份内存，只读被访问到的页 | 恢复链路：卷交接之后 20 个 VM 要约 110 s；跨 AZ 从 S3 恢复时，要先下载完整内存镜像 | **中**：缩短恢复时间，并且让「从 S3 直接恢复」成为可能。但它**不加快 checkpoint 写入**，对 120 s 窗口内能保存多少沙盒没有帮助 |
| **先缓存在本地，再异步上传对象存储**，并按块去重（memfile header） | pause 的关键路径上不做上传 | 本方案的 Spot 路径只写 EBS，跨 AZ 容灾要靠事后同步 | **中**：可以对应到「standby 恢复后，`zfs send -c` 增量同步到 S3」 |
| **rootfs 用 NBD COW，pause 时导出块级 diff**，并支持延后导出（reflink 后在后台封装） | rootfs 也能做增量，并且不占 pause 的关键路径 | 本方案的 rootfs 一直留在状态 EBS 上，不做快照；做跨 AZ 恢复时缺这一块 | 中 |
| **Pause 准入时检查磁盘余量**（内存 + rootfs cache + snapfile） | 磁盘不够时拒绝 pause，而不是写到一半失败 | 本方案没有任何准入控制（报告 E6） | **高**：做法简单，可以直接照搬到 node-agent |
| **每个沙盒用 `cpu.max` 配额限制 vCPU 线程** | 防止吵闹邻居 | CPU 争用实测：8 倍超分时空闲 VM 的 p99 达到 4.9 s | 中：保证交互延迟的下限。**但它不能绕开嵌套虚拟化的 vCPU 上限**，因为 VM 实际创建的 vCPU 数并没有减少 |
| **网络 slot 在本机池化**（netns + veth + tap） | 槽位可以复用 | 本方案的 `tap_idx` 是全局只增计数器（本轮已修复越界问题） | 低 |

**结论**：E2B 的快照「快」，主要快在 **resume**（按需分页 + 预取）和**不重复写 base**（以模板为 base，分层存储），而不是单次 checkpoint 的写入带宽。它同样受限于本机磁盘和网络带宽。

要扩大 120 s 窗口内能保存的沙盒数量，最值得借鉴的两点是：
1. **以模板内存快照作为共享 base**；
2. **周期性原地 checkpoint**，让 Spot 时刻只需要写最后一段增量。

这两点和本轮已经验证过的 ZFS 原地合并组合使用，理论上可以把窗口内需要写入的数据量从「全部脏页」降到「最近一个 checkpoint 周期内的脏页」。**这两点已经在 §11 中做了真机验证**：模板 base 把 Spot 写入量降为三分之一；周期 checkpoint 在热点负载下把 120 个沙盒的 Spot 用时从 110.8 s 降到 42.2 s，但在脏页均匀分布时反而更差。落地前要先测出客户负载在一个周期内碰到的 record 数量，再决定是否开启以及周期取多长。

## 11. 追加实验：周期性原地 checkpoint 与模板共享内存 base（2026-10-17）

§9 里提出了两项可能加快 Spot 快照的手段，这一节在真机上把它们逐一测了。环境和 §0 相同：两台 r8i.8xlarge，节点 A 的状态盘是 XFS，节点 B 是 ZFS（lz4，rs=1M）。node-agent 来自分支 `claude/snapshot-accel-bench`，新增了三个实验接口：`/vm/checkpoint`、`/vm/template_publish`、`/vm/create_from_template`。测试脚本是 `scripts/bench/accel_bench.py`。为了在合并 main 的安全修复之后仍能直连 node-agent，测试在目标节点上的 runner Pod 里运行（`scripts/bench/runner.yaml`）。测试期间关闭了 Spot 恢复控制器，避免它干扰测试。每次触发 Spot checkpoint 前都会冻结 guest 负载并记录 sha256，事后抽 3 个 VM resume 比对。**下表中跑完的场景，恢复抽检都是 3/3 一致**。模板的首轮（59.4 s）resume 失败，原因是 11.4 第 2 项，修复后重跑得到 78.6 s 那一行。

### 11.1 结论

| 手段 | 能不能让 Spot 快照更快 | 关键数据 |
|---|---|---|
| **周期性原地 checkpoint** | **取决于脏页的分布。改写集中在热点工作集时效果很大；整块内存均匀随机改写时反而更差** | 热点 10%：120 个沙盒从 **110.8 s / 109 GiB 降到 42.2 s / 19.8 GiB**（1 MiB/s），5 MiB/s 时 53.9 s / 31.8 GiB。均匀随机：从 119/120 **降到 82/120** |
| **模板共享内存 base** | **能，而且省下的主要是 base 和 context 的写入量**；Spot 窗口内的写入量降为三分之一 | 60 个沙盒：Spot 写入 **84.4 → 28.9 GiB**，用时 103.9 → 78.6 s；不用再做 Full base（原来 130 s / 120 GiB）；宿主内存占用 85 → 27 GiB |

两者都没有改变 §3 的基本规律：120 s 窗口里能保存多少个沙盒，取决于「触发时刻还没落盘的脏页量 ÷ 有效写入带宽」。周期 checkpoint 减少的是「还没落盘」的部分，模板 base 减少的是「需要落盘」的部分。

### 11.2 周期性原地 checkpoint（节点 B，ZFS，`bench-results/t3-accel-periodic.jsonl`）

**做法**：
1. 后台按周期对每个运行中的沙盒做一次 checkpoint：先 `cp --reflink` 把 base 克隆一份。
2. 暂停 VM，写 Diff 到克隆文件里，再恢复运行。
3. 用合并后的文件替换 base。

Firecracker 每做完一次 Diff 快照就清空脏页位图，所以 Spot 通知到来时，只需要写上一次 checkpoint 之后新产生的脏页。

**负载**：120 个 2 GiB 沙盒，先打 base，再让每个 guest 填 1200 MiB（mixed 内容）。之后按 R MiB/s 持续改写，稳态观测 180 s 后触发 Spot。checkpoint 周期 60 s，并发 4 路。

| 场景 | 后台写盘 | checkpoint 暂停 p50 / p99 | 触发时距上次 checkpoint p50 | **Spot 结果** | 写入量 | 单 VM p50 |
|---|---:|---:|---:|---:|---:|---:|
| 不做周期 checkpoint，R=5 | 1.7 MiB/s | — | — | 113/120，111.3 s（撞上截止时间） | 106.2 GiB | 6.9 s |
| 不做周期 checkpoint，R=1 | 1.8 MiB/s | — | — | 119/120，110.8 s（撞上截止时间） | 109.2 GiB | 6.7 s |
| 均匀随机，R=1 | **632 MiB/s** | **5.3 s / 7.2 s** | 80 s（跟不上 60 s 周期） | **82/120**，116.6 s | 66.4 GiB | 10.9 s |
| 均匀随机，R=5，串行 | 434 MiB/s | 4.0 s / 4.6 s | 实际周期约 470 s | 中途连接被重置，没有跑完（见 11.4） | — | — |
| **热点 10%，R=1** | 354 MiB/s | **0.57 s / 1.36 s** | 30 s | **120/120，42.2 s** | **19.8 GiB** | 2.3 s |
| **热点 10%，R=5** | 687 MiB/s | 1.13 s / 3.28 s | 31 s | **120/120，53.9 s** | 31.8 GiB | 2.9 s |

第一轮 checkpoint 要把填充期的全部脏页写一遍：120 个沙盒用时 122～126 s，约 110 GiB。所以系统必须在稳态下运行一段时间，这项优化才开始生效。新建的沙盒在完成第一轮 checkpoint 之前，Spot 容量和不做周期 checkpoint 时一样。

**为什么均匀随机反而更差**：ZFS 以 record（1 MiB）为单位做写时复制。memtouch 的改写在 1200 MiB 内均匀随机，一个周期里约 80 MiB 的零散 4K 页几乎会碰到每一个 record，所以每次 checkpoint 实际上要把整份内存重写一遍。后台写盘 632 MiB/s，而理论上的唯一脏页速率只有 120 MiB/s，**放大了 5 倍多**。结果有三个：
- 实例 EBS 带宽有一半被后台 checkpoint 占掉；
- 4 路并发时，每次暂停 VM 5 s 以上；
- 触发时每个 VM 仍有约 80 s 的脏页没有落盘，加上 ZFS 的写入积压，Spot 反而只保存了 82 个。

热点场景下，每次 checkpoint 只碰热区（120 MiB）里的 record，放大有上限，于是暂停降到 0.6 s 左右，Spot 时刻只剩最近约 30 s 的增量。

**这项优化落地之前，需要先确认三件事**：
1. **先测客户真实负载的脏页局部性**：一个周期内被碰到的 1 MiB record 数，而不只是脏页数。可以对客户负载连续做两次 Diff 快照，然后统计 Diff 文件里非空的 record。只有局部性好的负载才适合开周期 checkpoint。
2. **ZFS 的 recordsize 要和这项优化一起调**：rs=1M 对 Spot 时刻的整体写入最有利（§3），但对周期 checkpoint 的写放大最不利。对于脏页零散的负载，状态盘可以考虑 64K～128K 的 recordsize（本轮未测）。
3. **限制 checkpoint 的速率和并发**：这项优化平时就要占用 EBS 带宽，还会在 checkpoint 时暂停 VM（热点场景约 0.6 s，最坏 5～8 s）。生产环境中应该按「checkpoint 暂停 p99 ≤ 1 s、后台写盘 ≤ 实例带宽的 30%」自适应调整周期，而不是固定 60 s。

在 XFS 上，这项优化每次 checkpoint 之后都要重算 base 的 sha256（每个沙盒冷读 2 GiB），所以本轮只在 ZFS（原地合并、靠文件系统校验完整性）上测试。

### 11.3 模板共享内存 base（节点 A，XFS，`bench-results/t3-accel-template.jsonl`）

**做法**：
1. 先把一个已经加载好 context（800 MiB，固定 seed）的沙盒发布成模板：暂停 2.3 s，生成 Full 内存、VM 状态和 rootfs 的 reflink。
2. 新沙盒直接从模板快照 load：`vm.mem` 以硬链接的形式作为该沙盒的 `vm.mem.base`，同一个 inode，所以页缓存共享，也不用再为每个沙盒写一份 Full base。
3. 网卡和 vsock 通过 snapshot load 的 `network_overrides` / `vsock_override` 改成自己的。Firecracker 不能覆盖 drive 路径，所以 rootfs 用 jailer 的 `--bind-alias` 挂到模板源的目录名下。
4. load 完成后，经 vsock 改写 guest IP。

**负载**：60 个 2 GiB 沙盒，每个 = 800 MiB 共享 context + 400 MiB 私有脏页（mixed）。

| 场景 | 建沙盒 | Full base | 宿主匿名内存 / FC RSS | **Spot 结果** | 写入量 | 单 VM p50 |
|---|---|---|---:|---:|---:|---:|
| 冷启动 + 各自打 Full base，之后再加载 context | 冷启动 | **130.1 s，写 120 GiB** | 85 GiB / 85 GiB | 60/60，103.9 s | **84.4 GiB** | 13.8 s |
| **从模板拉起** | **单个 0.4 s**（load 6～9 ms） | **不需要** | **27 GiB / 36 GiB** | **60/60，78.6 s**（首轮 59.4 s） | **28.9 GiB** | 10.2 s |
| 冷启动，没打 base 时 Spot 就到来（最坏情况） | 冷启动 | 无 | 87 GiB / 86 GiB | **25/60**，115.4 s（只能做 Full 快照，每个约 36 s） | 52.0 GiB | 35.9 s |

结论：
- **Spot 窗口内的写入量降为三分之一**：context 已经在模板里，Spot 时只需要写私有脏页。
- **省掉了每个沙盒 130 s / 120 GiB 的 Full base**：这一步原本要和沙盒创建抢带宽；如果 Spot 到来时 base 还没打完，就会退化成最坏情况那一行，60 个里只能保存 25 个。
- **附带的收益是内存**：60 个沙盒共享同一份 context 页缓存，宿主匿名内存从 85 GiB 降到 27 GiB，可用内存多出约 59 GiB。这正是 §2.3 里 AL2023 没有 KSM 时想要的「同内容页共享」。
- 用时只降了约 24%，没有像写入量那样降到三分之一：29 GiB / 78.6 s ≈ 380 MiB/s，远没有达到 EBS 带宽上限。说明在 XFS 上，瓶颈已经从写入带宽转移到了单 VM 的稀疏 Diff 合并和校验处理上（本轮没有深入剖析）。两次运行分别是 59.4 s 和 78.6 s，波动也比较大。

**局限**：
- 只有「同一模板拉起的沙盒共享同一份 context」时才有收益。context 各不相同的沙盒，仍然要按冷启动处理。
- 从模板 load 的 VM 会继承模板的 guest 状态，包括随机数熵池、系统时间、主机名和进程 PID。生产环境中，load 之后必须重新播种熵池、校准时钟，并且不能把会话密钥放进模板。
- ZFS 上没有测这项：ZFS 的 Full base 本来就因压缩只写 4.4 GiB / 15 s（`t3-accel-periodic.jsonl` 中的 base_s），所以模板 base 在 ZFS 上的收益主要来自 context 不需要再写一遍，而不是省掉 base。

### 11.4 本轮发现并修复的问题

| # | 问题 | 修复 |
|---|---|---|
| 1 | node-agent 用默认的 `ThreadingHTTPServer`，listen backlog 只有 5，并发请求一多就 `ConnectionResetError` | `request_queue_size=128`、`daemon_threads=True` |
| 2 | 从模板拉起的沙盒 suspend 之后再 resume，找不到 rootfs（快照里固化的仍是模板源的路径） | 建沙盒时写 `template.source`，每次 resume 都挂同一个 `--bind-alias` |
| 3 | 均匀随机改写下，周期 checkpoint 在 ZFS rs=1M 上写放大 5 倍以上，并把 VM 冻结 4～8 s | 没有修复：属于设计约束，见 11.2 的落地前提 |

**这三个实验接口已随 #36 合入 main，但还没有加进控制面的调度，也没有开关**。要落地，还需要：checkpoint 的自适应调度、模板管理（发布、版本、回收），以及 guest 去重（熵池、时钟）。

## 12. 追加实验：嵌套虚拟化 `KVM_EXIT_FAIL_ENTRY` 排查与绑核（2026-10-19）

环境：独立 EC2 r8i.8xlarge（嵌套虚拟化，32 vCPU），AL2023 内核 6.18.54，microcode `0x1000434`，Firecracker v1.16.1。没有经过 EKS 和 node-agent。每个 VM 配 1 vCPU / 128 MiB（E5 为 96 MiB），共享只读 rootfs，不配网卡。每增加一档 VM 后观察 120 s（E5 为 180 s）；某档出现失败后，若下一档也失败就停止加压。

- 脚本：`scripts/bench/failentry-probe.sh`
- 原始数据：`bench-results/t4-failentry-probe.jsonl`
- 一份完整的 VMCS dump：`bench-results/t4-failentry-vmcs-dump.txt`

### 12.1 结论

- **触发条件是 VM 的 vCPU 线程在宿主 CPU 之间迁移。** 把每个 VM 用 `taskset -c <n>` 绑定到单个宿主 CPU 后，**1920 个 VM（60:1）0 失败**。不绑核时，288 个就开始失败。
- **只绑到 4 个 CPU 一组无效**：失败数和不绑核几乎一样，说明只要在多个 CPU 之间迁移，就会触发这个错误。
- **偶发迁移是安全的**：绑核之后，把全部 384 个 VM 整体改绑到下一个 CPU，连续 3 轮都是 0 失败。所以 node-agent 可以低频地做负载再均衡。
- **已排除的因素**：
  - VMX preemption timer：`preemption_timer=0` 后 PinBased 变成 `0xbf`，照样失败；
  - VPID 耗尽：失败 VM 的 VPID 在 4～358 之间随机分布；
  - APICv / PML、宿主内核版本、EKS：见 §2.1。
- **VMCS 特征**：`PinBased=0x000000ff`、`EntryControls=0x53ff`、`ExitControls=0xbefff`，上一次退出原因是 HLT（0xc）或外部中断（0x1），每次失败都相同。失败发生在冷启动，与快照无关，并且在裸金属上不复现。
- **推断**（需要 AWS 确认）：缺陷在 Nitro 处理嵌套 VM 的 vCPU（VMCS）跨 L1 CPU 迁移的路径上。VM 越多，迁移越频繁，触发概率越高，所以看起来像是一个"按宿主 vCPU 线性增长的上限"。

**快照"年龄"对照**：恢复一个存放很久的快照时，VMCS 里会出现很大的负 TSC offset（数值约等于快照的存放时长），需要确认这会不会触发同样的错误。我们做了两次恢复对照，8 个 VM 做 Full 快照，在同一台嵌套宿主上不绑核恢复：
- 存放 70 s 后恢复：8/8 存活；
- 存放 **6.0 小时**（21728 s）后恢复：**8/8 存活，0 失败**。

在低密度下没有复现这个问题。

### 12.3 落地建议

1. `scripts/sbx-vmm-runtime` 用 `systemd-run` 启动 VM 时，加 `--property AllowedCPUs=<n>`。这是 cgroup cpuset，对该 unit 的全部线程生效。
2. node-agent 在 create / resume / 从模板 load 时，按"每个 CPU 上已绑定的 VM 数最少"选 `<n>`，并把它记进 VM 状态。
3. 多 vCPU 的 VM 要把每个 `fc_vcpu N` 线程分别绑到不同的 CPU 上。这一项尚未验证。
4. CPU 繁忙时失去了内核的自动负载均衡，需要由 node-agent 低频地把热点 VM 改绑到空闲 CPU 上。E6 已证明改绑是安全的，但频率必须远低于内核调度器的迁移频率。
5. 绑核落地并在完整链路上验证（node-agent、jailer、tap 网络、快照、负载）之前，生产上限仍按 1:8 执行。
6. 建议把本节数据和复现脚本提交给 EC2 嵌套虚拟化团队，确认根因和修复计划。

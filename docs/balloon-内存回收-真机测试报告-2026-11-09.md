# virtio-balloon 内存回收：设计与真机测试报告（2026-11-09）

> 所有数据都在 AWS us-east-1 真机上测得：集群由 Terraform（stage1 → phase3 → stage2）从零拉起，测试由 `scripts/bench/balloon_bench.py` 在沙盒节点的 bench-runner Pod 里直接驱动 node-agent（HMAC 签名）。
> 原始数据在 `bench-results/b*.jsonl`，每张表都注明了对应文件。

## 0. 背景与结论摘要

改动前，每个 VM 都挂了 virtio-balloon，开了 free page reporting（FPR），但没有开统计，目标值固定为 0，也没有宿主侧的回收策略。我们对照《Memory Ballooning — A Technical Deep Dive》（Junhui Liu，2026-10）以及 Firecracker v1.16.1 官方文档和源码，补上了缺的这部分。

| 问题 | 文档 / 业界做法 | 本项目实现 | 真机结果 |
|---|---|---|---|
| FPR 只交还空闲页，碰不到 guest 的 page cache | 传统充气（inflate）才能强制回收和设上限 | 宿主压力驱动的气球控制器（`node-agent/balloon.py`） | 只靠 FPR：guest 攒满 3.3 GiB 缓存后，宿主侧不回落；充气 1.0 s 回收 **2.6 GiB**（§2） |
| virtio-balloon 本身不带策略，目标值要由上层决定 | oVirt MoM / ESX share-out：滞回、保底、空闲 VM 优先；senpai 用 PSI 作压力信号 | 高低水位滞回（0.80 / 0.65），每 VM 保底 max(256 MiB, 10%)，单 VM 气球最多占 75%，空闲 VM 优先，步长随压力线性放大，PSI 也可触发 | 8 VM 压力测试：slice 使用率从 **91% 压到 65%**，zram 换出从 **5.1 GiB 降到 0.96 GiB**，swap 超过 1 GiB 的时长从 **126 s 降到 10 s**，0 OOM（§3） |
| 宿主看不到 guest 内存（语义鸿沟） | 开 virtio-balloon stats；不要把统计当成保证 | 默认 `stats_polling_interval_s=5`（只能在 boot 前开）；`fc_balloon_*` / `fcnode_vmm_*` 低基数指标；`GET /balloon/status`、`GET /vm/{id}/balloon` | 单 VM 宿主内存拆成 anon（guest RAM）和 file（宿主缓存）两部分（§2） |
| 充气过度会让 guest OOM 或抖动 | 设保底；`deflate_on_oom`；看到 guest 吃紧就放气 | major fault 速率、swap-in、可用内存低于保底的一半 → 放气一步并冷却；发现 `deflate_on_oom` 触发 → 目标对齐 actual；充气停滞 → 目标对齐 actual | guest 在气球已充满时申请 2.5 GiB：成功，0 OOM，控制器连续 distress 放气到 488 MiB（§4） |
| free page hinting | 主要用于热迁移 | **不启用**：Firecracker 文档标注为 developer-preview，存在可能破坏 guest 内存的竞态 | — |
| 打快照前先充气能否让快照变小 | 业界常见做法 | **不做**：Firecracker v1.16 的 Full 快照（`dump()`）把整块 guest 内存写满，零页也写 | 充气 3 GiB 与不充气，`mem_actual_bytes` 都是 4 GiB；suspend/resume 后 sha256 一致，气球状态和统计都保留（§5） |
| 气球是 best-effort，guest 不可信 | Firecracker 安全声明：宿主必须能承受 VM 用满 boot 时的全部内存 | 控制器只做优化，不参与准入；硬保障仍是 `sbx.slice` MemoryMax + zram + 每 VM service MemoryMax | 突发写入时 slice 仍会短暂到上限（§3），由 zram 兜底 |

## 2. FPR 与 page cache：单 VM（`bench-results/b1-cache.jsonl`）

宿主侧内存取自该 VM 的 systemd service cgroup。anon 约等于 guest RAM 实际占用的宿主内存；file 是宿主为 `rootfs.ext4` 缓存的磁盘页（干净页，宿主可以回收）。

| 阶段 | 宿主 anon（guest RAM） | 宿主 file | 气球 | guest MemAvailable | guest Cached+Buffers |
|---|---:|---:|---:|---:|---:|
| 空闲 | 207 MiB | 33 MiB | 0 | 3784 MiB | 25 MiB |
| 攒满 page cache | **3489 MiB** | 1593 MiB | 0 | 3694 MiB | 3272 MiB |
| 只靠 FPR，30 s 后 | **3490 MiB**（不回落） | 1589 MiB | 0 | 3695 MiB | 3272 MiB |
| 充气到 3182 MiB（**1.0 s**） | **891 MiB** | 1589 MiB | 3182 | 528 MiB | 607 MiB |
| 放气到 0（0.5 s） | 891 MiB（不回涨） | 1589 MiB | 0 | 3709 MiB | 607 MiB |
| 重读 1.2 GiB 文件（4.2 s） | 2023 MiB | 2043 MiB | 0 | 3710 MiB | 1807 MiB |
| guest `drop_caches`，15 s 后 | 243 MiB | 2045 MiB | 0 | 3791 MiB | 10 MiB |
| guest 写 1.5 GiB 匿名内存后释放，15 s 后 | 249 MiB | 2046 MiB | 0 | 3789 MiB | 13 MiB |

结论：

1. **只靠 FPR 拿不回 page cache**。guest 的 MemAvailable 仍有 3.7 GiB（缓存都可回收），宿主却始终为它付着 3.5 GiB。这就是文档说的语义鸿沟。
2. **充气 1 s 内回收 2.6 GiB**，放气后宿主内存不回涨：页还给 guest，但 guest 不碰就不会再占宿主内存。guest 驱动的速度不是瓶颈。
3. FPR 对真正释放的内存有效：`drop_caches` 后，以及匿名内存释放后，15 s 内宿主 anon 都降回约 250 MiB。
4. **意外发现：磁盘页被缓存了两份**。guest 读写 `/dev/vda` 时，Firecracker 经宿主 page cache 读写 `rootfs.ext4`，同一份数据宿主也缓存一份（file 1.6 到 2 GiB），并计入该 VM 的 cgroup。第一版用 `memory.current` 判断压力时，它会被当成压力。最终版改用 kubelet/cAdvisor 的 working set 口径（`memory.current − inactive_file`）。

## 3. 宿主压力：8 VM 同时攒 page cache（控制器关 / 开）

`bench-results/b2-pressure-off.jsonl`（`balloon_auto_reclaim=false`，只采集统计）和 `bench-results/b2-pressure-on.jsonl`（默认开启）。流程：8 个 4 GiB VM 同时攒约 3.3 GiB 缓存 → 保持 60 s → 4 个 VM 重读文件 → 保持 60 s → 销毁 4 个 → 观察 90 s。每 2 s 采样一次，同时对 1 个 VM 做 exec 探测。另有 3 个控制面暖池 VM 常驻。

| 指标 | 控制器关 | **控制器开** |
|---|---:|---:|
| 持续阶段 slice 使用率（working set） | 91%（25.3 GiB） | **65%（18.1 GiB）** |
| slice 峰值（突发瞬间） | 98% | 99%（随后 16 s 内压到 65%） |
| zram 换出的 guest 内存（持续阶段平均 / 峰值） | 5.1 / 5.1 GiB | **0.96 / 1.4 GiB** |
| swap 超过 1 GiB 的时长 | 126 s | **10 s** |
| 测试结束后残留在 zram 的内存 | 611 MiB | 440 MiB |
| PSI memory some avg10 峰值 | 25.8 | 23.5 |
| exec 探测：p50 / 最大值 | 4 ms / 41.3 s | 4 ms / 29.5 s（复测 45.5 s，见 §9） |
| 8 VM 攒缓存耗时 p50 | 41.8 s | 33.1 s（复测 45.8 s，见 §9） |
| 4 VM 重读 1.2 GiB 文件 | 2.3 到 2.9 s | 4.6 到 4.8 s |
| 气球最多回收 | — | **15.4 GiB** |
| guest OOM | 0 | 0 |
| 控制器动作 | — | 33 次 reclaim，57 次 release |

解读：

- **不开控制器时，宿主只能盲目换页**：guest 的 page cache 在宿主眼里就是匿名页，被换进 zram，持续阶段一直有 5 GiB。这正是文档说的 hypervisor swapping 性能杀手。开了控制器后，guest 按自己的回收顺序（空闲 → 干净缓存）交出页，宿主几乎不用换页。
- **突发仍会顶到上限，突发瞬间的卡顿控制器改善不了**：8 个 VM 同时以合计约 1.5 GiB/s 的速度写缓存，比 5 s 的决策周期快，slice 仍会短暂到 99%，由 zram 兜底。控制器在接下来 2 到 3 个周期内收回 11 到 14 GiB，把使用率压回低水位。所以硬保障必须仍是 slice + zram，控制器负责缩短压力持续的时间。突发瞬间的 exec 卡顿和攒缓存耗时在不同轮次间波动很大（开启时 29.5 s 和 45.5 s 两轮，关闭时 41.3 s），不能当成控制器的收益。
- **代价**：被回收的是 guest 的 page cache，重读文件要重新走磁盘（2.5 s → 4.7 s，仍命中宿主缓存）。这是"牺牲冷缓存，换整机不进 swap"的取舍，可以通过 `balloon_reclaim_high` / `balloon_reclaim_low` 调节。
- **归还是渐进的**：销毁 4 个 VM 后压力降到低水位以下，气球按每 VM 每周期 128 MiB 慢慢放，80 s 内从 7.1 GiB 放到 0.3 GiB，没有来回震荡。

## 4. guest 吃紧：气球已充满时 guest 突然要内存（`bench-results/b3-distress*.jsonl`）

VM 先攒满缓存，充气到 3183 MiB（guest 只剩 525 MiB 可用），然后在 guest 里申请 2.5 GiB 匿名内存并逐页写入。

| 版本 | 结果 | 气球 target / actual | guest OOM |
|---|---|---|---|
| 第一版（`b3-distress-run1-execlock.jsonl`） | 申请成功（29 s） | 3183 / **1256**：只有 `deflate_on_oom` 生效，**控制器没有任何动作** | 0 |
| 最终版（`b3-distress.jsonl`） | 申请成功（28.6 s） | **488 / 488**：控制器每个周期判定 distress，依次放到 1437 → 1000 → … → 488 | 0 |

第一版的问题：`/vm/exec` 整个执行期间都持有 VM 操作锁，控制器非阻塞拿锁失败就跳过这个 VM。也就是说，guest 跑长命令、最需要内存的时候，控制器反而管不到。最终版拆出单独的"气球锁"，只让 create / destroy / suspend / resume / checkpoint 这些生命周期操作和控制器互斥；exec 只走 vsock，不持有气球锁。单测里也加了这个用例。

## 5. 快照：充气状态下 suspend / resume（`bench-results/b4-snapshot.jsonl`）

| 变体 | suspend（Full） | `mem_actual_bytes` | resume | memtouch sha256（512 MiB mixed） | 恢复后的气球 / 统计 |
|---|---:|---:|---:|---|---|
| 不充气 | 33.1 s | 4 GiB | 7.9 s | ✅ 一致 | amount 0 / 统计正常 |
| 充气约 2.6 GiB | 26.0 s | **4 GiB** | 7.7 s | ✅ 一致 | amount 保留（2526 MiB）/ 统计正常 |

- Full 快照不会因为充气变小（和 Firecracker 源码一致：Full `dump()` 写满整块内存），所以没有做"打快照前先充气"。suspend 耗时的差异只有一组样本，不作为结论。
- 气球配置（包括 `stats_polling_interval_s`）随快照保存，resume 后控制器能直接接管。在没有压力的节点上，它会按归还速度慢慢放气。
- `b4-snapshot-run1/run2` 两组 sha256 为空，是测试脚本的问题（`nohup` 下 PATH 不全；`pkill -f` 匹配到了执行命令的 shell 自身），与 node-agent 无关，保留作记录。

## 8. 已知限制与后续

- 气球依赖 guest 驱动配合，统计由 guest 上报，都不可信。**容量规划和准入不能扣掉气球的回收量**，最坏情况仍要按 `mem_size_mib` 计算。控制面的内存准入仍未实现。
- 改动之前创建的 VM、以及用旧快照恢复的 VM，统计是关闭的。控制器看不到这些 VM 的状态，不会给它们充气，`fc_balloon_vms{stats="unavailable"}` 会单独计数。
- 磁盘页被缓存两份（guest + 宿主）仍然存在。干净页宿主能回收，影响不大；如果要进一步省内存，可以评估让 rootfs 绕过宿主缓存（例如 virtio-blk O_DIRECT），需要另外测 I/O 延迟。
- 持续处于充气状态，说明超分超过了安全线。建议对 `fc_balloon_reclaim_active` 持续为 1、以及 `fcnode_vmm_memory_bytes{kind="swap"}` 增长加告警。

## 9. 正式镜像复测（`bench-results/*-docker.jsonl`）

§2 到 §6 的镜像是在旧镜像上用 crane 追加代码层做的。之后在本机用 Colima 起了 docker，经 `scripts/build_and_push.sh --component node-agent --node-agent-platform linux/amd64` 正式构建 `node-agent:balloon-20261109-docker`。确认镜像内 4 个源码文件和仓库一致、在镜像的 Python 3.12 下单测全部通过之后，用 Terraform 部署，同一集群上把四个场景重跑一遍：

| 场景 | 复测结果 | 与前文对比 |
|---|---|---|
| cache（`b1-cache-docker`） | 只靠 FPR 等 30 s，guest RAM 仍为 3489 MiB；充气 1.5 s 降到 891 MiB；`drop_caches` 后 239 MiB，匿名内存释放后 246 MiB | 一致 |
| distress（`b3-distress-docker`） | 申请 2.5 GiB 成功（28.6 s），0 OOM；控制器动作 release → distress ×3 → release，target / actual 最终 488 / 488 | 一致 |
| snapshot（`b4-snapshot-docker`） | 两个变体的 sha256 都一致；Full 快照都是 4 GiB；充气变体恢复后气球保持 2525 MiB，统计正常 | 一致 |
| 端到端回归（`b5-e2e-regression-docker.log`） | 16 项全部 PASS | 一致 |
| pressure 开启（`b2-pressure-on-docker`） | 持续阶段 working set 18.1 GiB（65%），swap 平均 0.97 GiB，超过 1 GiB 的时长 4 s，峰值 swap 1.6 GiB，气球最多回收 19.1 GiB，0 OOM | 持续阶段一致；突发阶段 exec 最长 45.5 s、攒缓存 p50 45.8 s，比上一轮差 |

突发阶段变差的原因：这一轮开始时，宿主 slice 里已经有 6.1 GiB working set（前面场景留下的宿主页缓存），上一轮是 2.5 GiB，压力更早顶到上限。这说明突发写入期间的卡顿主要由宿主换页和 I/O 决定，控制器 5 s 的决策周期赶不上。**控制器稳定的收益在持续阶段（使用率、swap 量和持续时长），不在突发瞬间。**

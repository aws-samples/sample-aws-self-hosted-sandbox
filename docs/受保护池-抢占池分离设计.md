# 受保护池 / 抢占池分离(Pool Separation)设计总结

> **本分支范围(基于当前 main 重做)**:仅 **M2 池分离**(节点自证池归属 + 控制面按池放置)。
> - 已含:`node-agent`(IMDS 自证 pool + 心跳上报)、`drivers/firecracker.py`(池感知选点 + 软约束回退)、`app.py`(放置策略)、`terraform`(`sandbox_capacity_type` 变量,非破坏)。
> - **未含(留作后续,依赖 main 尚无的机制)**:
>   - **M3 活动信号否决**:依赖自动跨机重调度(reschedule pass),当前 main 的 reconcile 只标 `needs_reschedule` 不自动拉起,故 M3 暂缓。
>   - **受保护池 + 抢占池双节点组拓扑**:main 采用方案C(单 AZ 持久状态 EBS),与"抢占池多 AZ + S3 权威"存在架构取舍,需与方案C owner 对齐后再落。当前仅提供 `sandbox_capacity_type` 让单个沙盒节点组可切 SPOT。
>
> 下文保留完整设计(含 M3)作为背景参考;实际本分支落地以上述范围为准。
>
> 影响文件(本分支):`node-agent/main.py`、`sandbox-api/drivers/firecracker.py`、`sandbox-api/app.py`、`terraform/phase3/main.tf`

---

## 1. 背景与动机

平台用 Spot 实例承载 Firecracker microVM 沙盒以省成本,配合"spot 回收 → 疏散快照到 S3 → 其它节点恢复"链路(M1/M4 已完成)。但纯 Spot 有个体验问题:

- **活跃/交互中的沙盒被 Spot 抢占中断**,即使能在别的节点秒级恢复,用户侧仍会感到卡顿/断连。典型场景:openclaw 会话正在跑任务、用户正在装环境。
- **空闲沙盒放在 on-demand 上是浪费**:它们即使被抢占,恢复代价也可忽略。

因此引入**池分离**:把节点分成两类,按沙盒"是否活跃"决定放哪。

| 池 | 计费类型 | 特点 | 承载谁 |
|---|---|---|---|
| `protected` | on-demand | 不会被回收 | 活跃 / 交互中的沙盒 |
| `spot` | spot | 便宜,随时可能被回收 | 空闲 / 可疏散的沙盒 |

**核心设计原则:池是"软约束"(优化)而非"硬约束"。** 目标池没有可用节点时,一律回退到任意活节点 —— 宁可跨池放置,也绝不让创建/恢复失败。池分离是为了省钱和体验,不能成为可用性的单点。

---

## 2. 目标

1. 每个节点能自证其池归属,并上报给控制面。
2. 创建沙盒时能按策略选择目标池(默认落 `protected`)。
3. 跨机重调度(M4)时,按沙盒活跃度决定落哪个池(M3 活动信号否决)。
4. **完全非破坏、可回滚**:不开启时(单池集群)行为与改动前完全一致。

---

## 3. 整体数据流

```
                 IMDS instance-life-cycle
                 ("spot" / "on-demand")
                          │
                          ▼
   node-agent  _detect_pool() ──(缓存)──► 心跳上报 pool 字段
                          │                    │
                          │                    ▼
                          │            DynamoDB claude-sbx-nodes
                          │            { ip, free_mem_mib, pool, ... }
                          ▼                    │
                                               ▼
   control-plane  create/reschedule ──► driver._pick_node(pool=?)
                          │                    │
              _placement_pool()          _pick_from_registry(): 先按池过滤,
              _reschedule_pool()         挑空闲内存最高且可达的节点;
              (决定目标池)               目标池无节点 → 回退不限池
```

要点:**池归属由节点自己经 IMDS 探测,控制面不需要任何额外注入或配置**。控制面只是消费心跳里的 `pool` 字段做放置决策。

## 4. 逐文件改动与原因

### 4.1 `node-agent/main.py` —— 节点自证池归属

新增 `_detect_pool()`:
- **优先级 1**:环境变量 `NODE_POOL`(`spot`/`protected`)显式覆盖 —— 供本地测试 / 特殊编排。
- **优先级 2**:查 IMDS `/latest/meta-data/instance-life-cycle`。返回 `spot` → `spot` 池;`on-demand` 或其它 → `protected` 池。
- **兜底**:IMDS 不可达(非 EC2 本地环境)→ 默认 `protected`(保守:当作"不会被回收",避免把沙盒误当成可随意疏散)。
- **单次探测缓存**(`_POOL_CACHE`):节点生命周期内池归属不变,不必每次心跳都查 IMDS。

心跳 `_heartbeat_once()` 的 item 里新增一个字段:`"pool": {"S": _detect_pool()}`。

> 为什么走 IMDS 而不是靠 Terraform 注入标签?—— 节点自证最简单、最不易出错:spot 组的实例天然报 spot,on-demand 组报 on-demand,无需在 DaemonSet / userData 里额外传参,也不会因为配置漂移而错标。

### 4.2 `sandbox-api/drivers/firecracker.py` —— 池感知选点

- `_active_nodes_from_registry()` 返回值从 `[(ip, free_mem)]` 扩成 `[(ip, free_mem, pool)]`。**老节点没上报 `pool` 时默认 `protected`**(保守,避免把活跃沙盒误放到未知池)。
- 新增 `_pick_from_registry(registry, exclude, pool)`:在候选里按空闲内存降序,挑第一个"池匹配 + 可达(/health 兜底确认)"的节点;`pool=None` 表示不限池。挑不到返回 `None`。
- `_pick_node(exclude=None, pool=None)` 重构:
  1. 先在**目标池内**挑(`_pick_from_registry(..., pool)`);
  2. 目标池内没有可达节点 → **回退不限池**再挑一次(软约束的核心);
  3. 都没有才抛错。
- `create(..., pool=None)`:把 `pool` 透传给 `_pick_node`。

> 回退逻辑是这块的关键正确性保证:池分离永远不能让 create 失败。已用单测覆盖"请求 spot 但无 spot 节点 → 落到 protected 节点"。

### 4.3 `sandbox-api/app.py` —— 创建时的放置策略

新增 `_placement_pool(body, spec)`,优先级:
1. 请求体 `pool`
2. `meta.pool`
3. 环境变量 `DEFAULT_CREATE_POOL`(默认 **`protected`**)

**为什么新建默认落 `protected`**:刚创建的沙盒通常紧接着交互/装环境,这个阶段最不该被 Spot 抢占打断。省成本靠的是"空闲后自动休眠(slept)"和"重调度时落 spot",而不是"一创建就放 spot"。

其它配套:
- `POOL_PLACEMENT_ENABLED`(默认 `1`)总开关。设 `0` → `pool` 恒为 `None`(不限池),**完全回到改动前行为**,便于单池集群或快速回滚。
- 记录 `record["pool"]`(期望池),供观测/重调度参考;实际落点以 driver 返回的 `node` 为准。
- **指定了明确 `pool` 时跳过暖池(warm pool)**:暖池预热的 VM 池归属不确定(可能在任意池),要保证落到目标池就必须冷建。未指定 `pool`(`None`)时仍可用暖池,维持秒级创建。

### 4.4 `sandbox-api/reconcile.py` —— M3 活动信号否决

新增 `_reschedule_pool(rec)`,用于 M4 跨机重调度时选目标池:
- 池分离关 → `None`(不限池,原行为)。
- 看 `last_active_at`:距今 < `RESCHEDULE_ACTIVE_VETO_S`(默认 300s)→ 判定"活跃/交互中" → **否决 spot,落 `protected`**。
- 否则(空闲)→ 落 `spot`(便宜;重调度本就是被中断后恢复,再被抢占也能再次恢复)。

`_reschedule_one` 里把 `pool=_reschedule_pool(rec)` 传给 `_pick_node`。目标池无活节点时 driver 内部自动回退,不会因此重调度失败。

> 语义:重调度默认倾向便宜的 spot,但"最近还在用"的沙盒有一票否决权,避免刚恢复的活跃会话立刻又被 spot 抢占,来回颠簸。

### 4.5 `terraform/phase3/main.tf` —— 受保护节点组(opt-in)

- 把原来内联的节点组配置抽成 `local.sandbox_ng`,让**两个池的节点组复用同一套引导脚本**(Firecracker/内核/rootfs/暂存盘挂载),避免重复 ~100 行 heredoc。
- 新增变量 `protected_node_count`(默认 **0**):
  - `0` → **不创建**受保护节点组,完全非破坏,单池行为不变。
  - `≥1` → 额外创建 `sbxprot_${node_arch}` 节点组,强制 `ON_DEMAND`,`min=max=desired=protected_node_count`。
- 主节点组 `sandbox_${node_arch}` 仍受 `capacity_type` 控制(设 `SPOT` 即作抢占池)。

**池分离演示配置**:`-var="capacity_type=SPOT" -var="protected_node_count=1"`。

## 5. 配置项汇总

| 位置 | 变量 | 默认 | 作用 |
|---|---|---|---|
| node-agent | `NODE_POOL` | 空 | 显式覆盖池归属(测试用),空则走 IMDS |
| control-plane | `POOL_PLACEMENT_ENABLED` | `1` | 池分离总开关,`0`=回到不限池原行为 |
| control-plane | `DEFAULT_CREATE_POOL` | `protected` | 新建沙盒默认池 |
| reconcile | `RESCHEDULE_ACTIVE_VETO_S` | `300` | 活跃窗口(秒),内则否决 spot |
| terraform | `protected_node_count` | `0` | 受保护(on-demand)节点组台数,0=不创建 |

---

## 6. 安全 / 回退语义

- **软约束**:目标池无可用节点一律回退不限池,池分离不会造成不可用。
- **一键回退**:`POOL_PLACEMENT_ENABLED=0` 即恢复改动前行为;`protected_node_count=0` 即不建受保护节点组。
- **向后兼容**:老节点心跳没有 `pool` 字段时默认按 `protected` 处理,不会误判。
- **非破坏 Terraform**:`protected_node_count` 默认 0;实测 `terraform plan` 加受保护节点组为 **0 删除 / 0 替换**,现有 spot 节点组仅 `min_size` 微调。

## 7. 实测验证结果

集群:`10.0.101.248`(spot)、`10.0.103.35`(spot)、`10.0.102.200`(protected,新加 on-demand 节点)。

**池探测**:三台节点心跳分别正确上报 `pool=spot / spot / protected`(真实 IMDS instance-life-cycle)。

**放置策略**:

| 请求 | 落点 | 池 | 结果 |
|---|---|---|---|
| 默认策略 | 10.0.102.200 | protected | ✓ |
| pool=protected | 10.0.102.200 | protected | ✓ |
| pool=spot | 10.0.103.35 | spot | ✓ |
| pool=spot | 10.0.103.35 | spot | ✓ |

**单元测试**:48 个 smoke 测试全过;`_pick_from_registry` / `_pick_node` 回退逻辑单独跑过(spot / protected / 不限池 / exclude / 目标池空回退 五种场景结果全对)。

**M3 活动否决**:逻辑随 smoke 测试通过;在线演示需"杀节点触发 needs_reschedule",破坏性较大未在线跑,逻辑已就绪。

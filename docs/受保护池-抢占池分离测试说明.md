# 受保护池 / 抢占池分离(M2 + M3)测试说明

> 配套设计文档:`docs/受保护池-抢占池分离设计.md`
> 目的:说明本功能怎么测、测了哪些、怎么复现,便于他人回归验证或在此基础上加用例。
> 被测对象:`node-agent/main.py`(池探测)、`sandbox-api/drivers/firecracker.py`(池感知选点)、`sandbox-api/app.py`(放置策略)、`sandbox-api/reconcile.py`(M3 活动否决重调度)。

---

## 1. 测试方法论(总原则)

**分层验证:从纯逻辑到真实集群,越靠近生产的层级用例越少但越真。**

| 层 | 测什么 | 环境 | 特点 |
|---|---|---|---|
| L1 静态 | 语法 / 既有功能回归 | 本地 | 秒级,零依赖 |
| L2 纯函数单测 | 选点 / 池决策逻辑 | 本地(可注入假数据) | 确定性,能穷举边界 |
| L3 集群功能测 | 真实创建 → 真实落点 | 真集群(黑盒 API) | 端到端,断言实际结果 |
| L4 配置开关 | 运维旋钮 | 真集群(改 env) | 切换后验证,测完还原 |

几条贯穿全程的准则:

- **能用纯函数测的绝不上集群** —— 决策函数输入→输出确定,离线穷举边界最高效。
- **必须上集群的用"可控注入"代替"破坏性操作"** —— 例如 M3 不去真终止 EC2,而是直接把记录改成 `needs_reschedule` 模拟死节点分类结果。
- **所有网络交互都假设会抖,用重试兜底** —— EKS 公网 endpoint 和 `kubectl port-forward` 会间歇性超时,不加重试会把网络抖动误判成功能 bug。
- **断言看"实际落点"不看"请求参数"** —— 例如"请求 spot"必须反查它真落在 spot 池节点才算过。
- **测完不留痕** —— 删除测试沙盒、还原 env。

## 2. 前置环境

- 集群需要**同时有两种池的活节点**才能验证分离:`capacity_type=SPOT`(抢占池)+ `protected_node_count>=1`(受保护 on-demand 池)。本轮用了 2×spot + 1×protected(均 i7i.8xlarge)。
- 控制面镜像需含被测代码(改 `app.py`/`reconcile.py` 后要重建镜像 + `kubectl rollout restart`)。
- 访问方式:`kubectl port-forward svc/sandbox-control-plane 18000:80`,API key 走 `Authorization: Bearer <key>`。
- 池映射校验数据源:控制面 `GET /admin/nodes`(返回每个活节点的 `ip` 和 `pool`),据此把创建返回的 `node` 反查成池。

## 3. 分层用例

### L1 静态检查
- `python3 -m py_compile node-agent/main.py sandbox-api/app.py sandbox-api/drivers/firecracker.py sandbox-api/reconcile.py`
- 既有 48 个 smoke 测试(`sandbox-api/smoke_test.py`,基于 moto 模拟 DynamoDB/S3)回归:
  `cd sandbox-api && python3 -m unittest smoke_test`
- 通过标准:编译无错;48 tests OK。

### L2 纯函数单测(离线,确定性)

**选点与回退(driver)** —— 构造假节点注册表 `[(ip, free_mem, pool), ...]`,stub 掉 `_agent` 的 `/health`:
- spot 请求 → 落空闲内存最高的 spot 节点。
- protected 请求 → 只落 protected 节点。
- 不限池(None)→ 落全局空闲最高。
- exclude 掉目标池唯一节点 → 返回 None(交回退处理)。
- **请求 spot 但无 spot 节点 → 自动回退不限池、落 protected 节点**(软约束核心)。

**M3 池决策 `_reschedule_pool`** —— 喂不同 `last_active_at`:
- 近期活跃(10s)→ `protected`(否决 spot)。
- 空闲(3600s)→ `spot`。
- **边界值 299s → protected;301s → spot**(卡 `RESCHEDULE_ACTIVE_VETO_S` 默认 300s 两侧)。
- 无任何时间戳 → `spot`。
- 回退 `updated_at` 近期 → `protected`。
- `POOL_PLACEMENT_ENABLED=0` → 恒返回 `None`。

> 运行方式:`PYTHONPATH=<repo根> python3` 直接 import 目标函数注入参数断言(注意 `sandbox_api` 是指向 `sandbox-api` 的符号链接)。

### L3 集群功能测(端到端,黑盒 API)

**A. 放置策略矩阵**(建沙盒 → 反查落点池)

| 用例 | 请求 | 期望池 |
|---|---|---|
| A1 | 默认(不带 pool) | protected |
| A2 | `pool=spot` | spot |
| A3 | `pool=protected` | protected |
| A4 | `meta.pool=spot` | spot |
| A5 | `pool=banana`(非法) | protected(回退默认) |
| A6 | `pool=spot` + `meta.pool=protected` | spot(body 覆盖 meta) |

**B. 池内选点** —— 建 spot 沙盒,断言落在当前空闲内存最高的 spot 节点。

**C. suspend/resume 池稳定性** —— 建 protected 沙盒 → suspend → resume,断言仍回到同一 protected 节点、状态 running。

**E. M3 活动否决 · 端到端重调度**(核心新链路,用可控注入):
1. 建 spot 沙盒 → suspend(使 S3 有完整快照 base+diff+rootfs,可跨机恢复)。
2. **直接改 DynamoDB** 把记录置为 `state=needs_reschedule` 并写入指定 `last_active_at`(模拟 reconcile 对"死节点上 suspended 沙盒"的分类结果)。
3. 等真实 reconciler(leader,~20s 一 tick)自己跑完 `_reschedule_pass → _reschedule_pool 决策 → _pick_node(pool) → 从 S3 resume`。
4. 轮询到 running 后反查落点池。
   - active(idle 10s)→ 应从 spot **跨池搬到 protected**。
   - idle(3600s)→ 应落 spot。

### L4 配置开关(改 env + rollout,测完还原)
- `POOL_PLACEMENT_ENABLED=0`:默认创建与显式 `pool=protected` 的记录 pool 均为空 → 池被忽略,回到不限池行为。
- `DEFAULT_CREATE_POOL=spot`:默认创建落 spot;显式 `pool=protected` 仍落 protected。
- 操作:`kubectl set env deployment/sandbox-control-plane -n sandbox-system KEY=VAL` → 等 rollout → 测 → `KEY-` 卸载还原。

### 测试中发现并修复的产品 bug
`_placement_pool` 对**非法 pool 值**原本返回 `None`(变成不限池,还会误走暖池慢路径),与设计文档"非法值回退默认池"不符。已改为回退 `DEFAULT_CREATE_POOL`;重建镜像 + 重新部署后 A5 从 FAIL 变 PASS。

## 5. 踩过的坑(排查经验,供后来者少走弯路)

1. **幂等键跨轮复用**:测试脚本用固定 `idempotency_key`,第二轮 POST 会命中上一轮的旧记录(idempotency 短路直接返回旧状态),导致断言读到过时/旧代码产出的记录 → 假 PASS/假 FAIL。**解法:每轮用唯一前缀(时间戳)。**
2. **port-forward / EKS endpoint 抖动**:`kubectl` 和 HTTP 调用会间歇 `i/o timeout` / 空响应。**解法:所有调用封装重试;判定失败前多试几次。**
3. **`:latest` 镜像是否真更新**:`rollout restart` 后要确认 pod 真跑的是新代码(`imagePullPolicy=Always` 时会重拉;可 `kubectl exec` 进 pod grep 新代码标记确认),否则会拿旧镜像测。
4. **暖池路径干扰**:未指定 pool(None)且默认镜像时会走暖池 claim,该路径较慢,易让创建请求超时 → 记录停在 `creating`。指定明确 pool 会跳过暖池,行为更确定。
5. **断言口径**:`admin/nodes` 偶发返回空(抖动)会让"节点→池"映射查空 → 实际落点显示 `?`。此时结合返回的 `node` 和已知稳定的节点→池映射复核,别误判。

## 附录 A:m8i.2xlarge 机型试验 —— IO 与疏散并发实测

> 背景:评估用 m8i 替换 i7i 作节点机型。m8i **无本地 NVMe**(要 NVMe 得 m8id),`/var/lib/sbx`(快照暂存)落根卷 gp3;m8i **支持嵌套虚拟化**(可跑 Firecracker,已 AWS 文档确认)。
> 环境:单台 m8i.2xlarge(8 vCPU / 32 GiB),受保护池,根卷 gp3 provisioned **1000 MB/s / 6000 IOPS**。
> 方法:把节点用 N×2GiB 沙盒填满(每个 tmpfs+urandom 灌 ~1500MB 不可压内存 → 内存快照真实占用),再并发 suspend(=快照+传 S3),测总墙钟。脚本 `_tmp_m8i_io.py`。

### A.1 满载疏散耗时(全并发)

| 沙盒数 | 内存快照量 | 疏散总墙钟(< 120s 窗口) |
|---|---|---|
| 10 × 2GiB | ~17 GB | 58.5s |
| 14 × 2GiB | ~20.6 GB | 79.6s |
| 15 × 2GiB(~90% RAM) | ~24 GB | 89.1s |

约 **线性 ~5.5–6s/沙盒**;满载(~15–16 个)在 120s 内,余量 ~20–30s。高密度下**瓶颈从"打快照"转到"S3 上传"**(本地读争用 + 网络)。

### A.2 澄清:为什么摸不到 1250 MB/s 突发 —— 不是 credit,是并发度

一开始用**单流** `dd oflag=direct` 只有 150–325 MB/s,**8 并行流**能到 ~1000 MB/s。曾误判为"实例 EBS 突发 credit 不够"。用**控制变量法证伪**:

- 开一台**全新** m8i.2xlarge,**开机 1 分钟**立刻测:单流 325 MB/s,8 并行第一波就 **1024 MB/s**,和跑了 4.4 小时的老节点**完全一样**。
- ⇒ 差异来自**单流 vs 并行(队列深度)**,不是机器新旧/credit 累积。单线程直写队列深度=1 → 延迟受限,喂不满带宽;多流才能打满。
- **~1000 MB/s 天花板 = gp3 单卷 provisioned 吞吐上限(1000),不是实例 1250 突发。** 要冲 1250 需多卷 striping 或 io2,单卷摸不到。
- 教训:测吞吐必须用**多流/高队列深度**(fio iodepth / 并行);单流 dd 会严重低估,导致错误归因。

### A.3 疏散并发扫描 —— U 型曲线,最优 ≈ 6–8

同样 15×2GiB / 1500MB fill,只变 suspend 并发上限:

| 并发上限 | 疏散总墙钟 | snapshot_create 均 | s3_upload 均 |
|---|---|---|---|
| 3 | 84.2s | 2.8s | 11.6s |
| 5 | 73.1s | 4.7s | 15.5s |
| **8** | **70.5s** ⭐ | 7.6s | 22.8s |
| 15 | 89.1s | 22.3s | 58.9s |

- **U 型**:太低(3)喂不满节点资源;太高(15)抢 8vCPU/EBS/网络互相拖慢。甜区 **5–8**。
- **看单个操作耗时会误导** —— per-VM 耗时随并发单调上升,但**总墙钟**是 U 型;要看总时间。

### A.4 可落地结论

1. **`RECLAIM_EVAC_CONCURRENCY` 应按机型设,不是一个固定值走天下。** m8i.2xlarge(8 vCPU / EBS-only)最优 ~8;当前默认 20 在此机型上**偏高**(15 沙盒 89s vs 8 并发 70.5s,慢 ~19s)。i7i(32 vCPU + 本地 NVMe)能扛高得多的并发。
2. m8i 换 i7i 可行(嵌套虚拟化 OK),但**无 NVMe 是主要代价**:本地快照 IO 全走 EBS(单卷 ≤1000 MB/s),疏散余量比 i7i 薄;想更稳可换 m8id(带 NVMe)或更大 m8i(持续 EBS 带宽更高)。
3. 根卷别只看实例的 1250 突发数字 —— **绑定约束是卷的 provisioned 吞吐**(单 gp3 ≤1000)。

### A.5 诚实边界

- 疏散是用**控制面并发 /suspend** 驱动的(每 VM 走 lease + DynamoDB 状态机),非 node-agent 原生 `_evacuate_local` 线程池。后者少了每 VM 的租约/DynamoDB 往返,应**略快或持平**,量级一致;要完全保真需注入 spot 信号触发真实疏散路径。
- 各轮 create/fill 时间有波动(dd urandom CPU 受限),但**疏散(suspend)墙钟**是干净的测量对象。
